# A tagging method is served by MLflow's model server, from its committed folder

Any frozen tagging method can be served over HTTP, one method per model server: MLflow 3.16.1's scoring server (FastAPI on uvicorn), which answers `GET /ping` and `POST /invocations`, in a container behind nginx on port 8080. The served model is built from the committed method folder `assets/methods/<name>/model/`, never from the MLflow store: `python -m codeforces_tags.serving package --method <name>` saves it with `mlflow.pyfunc.save_model` as a model from code, whose entry file, `serving/entry.py`, loads the folder with `load_method` and the code's own registry, as the logged wrapper does ([ADR 0002](0002-method-folders-and-mlflow-wrapper.md)); `code_paths` carries the `codeforces_tags` package into the model, and its requirements are pinned from `uv.lock`, with no `uv.lock` copied in. The same command stages, in the gitignored build context `build/serving/<name>/`, the weight files the folder pins (`pretrained.json`, and `trained.json`, [ADR 0006](0006-trained-weight-cache.md)), each re-hashed against its pin while it is copied, a `uv export` of the image's dependency groups with their hashes, and `deploy/Dockerfile`; `build` makes the image `codeforces-tags/<name>:<git short sha>` (`-dirty` when a packaged input, the code, `deploy/Dockerfile` or the method folder, was uncommitted) and `:latest`. `package` refuses, before it deletes or writes anything, a method that is not registered or not frozen, a weight cache that misses a file, and, unless `--allow-dirty`, uncommitted code, `deploy/Dockerfile` or method folder. Then it writes into a staging folder, which replaces the previous build only once complete: a later failure (a weight list whose names would put a copy outside the staged `weights/` folder, a copied weight that is not its pin, `uv export`) removes the staging folder and leaves the previous build untouched. It writes only under `build/serving`, which may be a symlink to another disk, since images are large: the guard that keeps it from deleting any other folder compares resolved paths.

**MLflow's server, in an image of our own.** `deploy/Dockerfile` installs `requirements.lock.txt` with `pip install --no-deps --require-hashes`, then takes the method's name as `ARG METHOD` and labels the image with it, copies the weights then the model, and runs MLflow's own container entrypoint, `mlflow.models.container._serve('local')`: the line `mlflow models generate-dockerfile --env-manager local` writes, nginx on 8080 in front of uvicorn on `127.0.0.1:8000`. `ARG METHOD` and the label come after the dependency layers, since a build argument in scope enters the cache key of every later step: placed first, it would keep the three F2LLM methods, which have one lock, from sharing their nginx and wheel layers. One worker holds the model (`MLFLOW_MODELS_WORKERS=1`: each worker would load its own copy, 2,432 MiB of GPU memory for `f2llm_late_fusion`, as its one worker held in the container on the GPU, notebook 12), and the entry file's lock runs one prediction, so one GPU forward pass, at a time. `/ping` answers 200 only once the model has loaded, and every platform waits on it.

**The response says how each tag was decided.** Each problem's record holds the method's name, a 0/1 column per focus tag and, for a score method, each tag's `score: <tag>` and `threshold: <tag>`, the per-tag threshold that `predict_from_scores` applies (`ScoreMethod.tag_thresholds()`; `Infinity` for a tag never predicted); a method that calls an API adds `failed` and `cost_usd`. The model server first refuses the fields the command line refuses (`cli.check_fields`: a blank statement or solution, named by its row in the request), so a raw HTTP client gets no tags, and an API method sends no paid request, for an empty problem. The records come from the command line's own `cli.run_method`, so a score method scores each problem once, an API method prices each answer, and only the focus tags are returned. An API method takes exactly one problem per request: none or several is the command line's own `CliError` (more than one paid problem needs a cost cap, which a server has no place to take). The entry file re-raises a `CliError` as an `MlflowException` with no cause, which the scoring server answers as a 500 whose JSON message MLflow 3.16.1 wraps as `Failed to predict data '<frame repr>'. \nError: <message>`, with no traceback that could quote a provider's text. The HTTP client unwraps that message, and keeps the JSON message of any other failed answer; where the body is not JSON it falls back to the status line, which is the case of nginx's 502 and 504 (HTML pages), of a 415 (plain text) and of MLflow's own 504, `Request processing time exceeded limit`, whose content type says `application/json` though its body is not JSON.

**One image per method, the device chosen at deploy time.** The image installs `uv.lock`'s exact pins, whose PyPI torch wheel brings its CUDA libraries, so the same image runs on the CPU and on the GPU, as `CODEFORCES_DEVICE` (`auto`, `cpu` or `cuda`) says: every torch method reads it when it loads, and the compose profile, the Kubernetes overlay or SageMaker's `Environment` sets it. It replaces the F2LLM-only `CODEFORCES_F2LLM_DEVICE`, which `devices.requested_device()` refuses, naming the new variable: a device variable silently ignored, on a machine whose GPU once rebooted it, is the failure to avoid. A device given in code still wins (`latency-cpu` loads a ModernBERT bag on the CPU whatever the shell sets), and `cuda` with no visible GPU fails the load. The device is not a setting of any recipe: run records hold the device's value, never the variable's name, so nothing frozen changes.

**The weights are in the image**: exactly the files the method folder pins, so a container serves offline (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`) wherever it runs. The platforms are local Docker (a compose file that runs the model server only, profiles `cpu` and `gpu`, published on `127.0.0.1`), Kubernetes (a kustomize base, `cpu` and `gpu` overlays, and the per-method overlay that `serving manifests` writes) and SageMaker (scripts over the aws CLI, run only on the user's explicit go: they push about 8 GB and bill by the hour). An API method's key comes at run time, from `deploy/.env.serving` (gitignored) or the Kubernetes Secret `codeforces-tags-env`, and is never baked into an image; API methods are not deployed to SageMaker, whose model `Environment` would hold the key in plain text.

**Checks compare live predictions with the frozen rows and choose nothing.** `serving smoke` asks a running model server for the first 20 test-set problems, one request at a time, and compares them with the method's frozen test rows by the rule of `verify` level (a): scores within `max(score_atol, TUNING_EXPORT_TOLERANCE)`, a 0/1 flip only where the frozen score lies within `score_atol` of its threshold. It refuses an API method, whose new request is a new sample of the API ([ADR 0003](0003-api-methods-are-fixed-reference-models.md)), so its frozen rows are no reference, and every request is paid. The verification is local: compose on the CPU and on the GPU, kind with the small `tfidf` image, and SageMaker's container contract (`docker run <image> serve`) run on this machine. Under compose's `gpu` profile, the 20 answers of `f2llm_late_fusion` took 0.148 s at the median and 0.262 s at the slowest, against 3.40 s and 8.21 s on the CPU (notebook 12). `f2llm_late_fusion` is served and verified first: a local score method, whose one-problem latency was a median 0.14 s on the GPU and 3.0 s on the CPU (8.5 s at the slowest, under `PROBLEM.md`'s 10 s), with no API key. The command line's default stays `jev-statement-code` ([ADR 0008](0008-cli-default-method.md)).

**Notebook 12 serves live, and quotes what needs Docker, a GPU, kind or AWS.** Re-executed, it packages `f2llm_late_fusion` and serves it on the CPU with `serving.local` (`mlflow models serve` in a subprocess, with the environment the image sets), asks it about test-set problems and a typed one, then stops it. The Docker, compose, Kubernetes and SageMaker runs are shown as recorded outputs, each with its command and the date it ran.

**The Streamlit app is a client on the user's machine.** `apps/streamlit_app.py` runs locally, never in a container; it asks a model server about a test-set problem or a problem typed in, and holds layout only: its request, errors, form rules and tables live in `serving/client.py` and `serving/problems.py`. Its sidebar links the served method to what MLflow tracked about it, in the UI that `serving mlflow-ui` serves on `127.0.0.1:5000` from the project's store: the `tag-methods` experiment, the method's run (its dev out-of-fold metrics and frozen latencies, and its logged model, which holds the run record's parameters and the test metrics) and, for a prompted or Jev method, its versions in the prompt registry: each version its committed run record pins (only the four zero-shot methods' records pin any), then those linked to its run in the store, which is how Jev's `jev-tags` reaches the app. `serving/mlflow_links.py` reads the experiment, the run and the run's linked prompt versions over MLflow's REST API, since their ids belong to one store; a store not yet rebuilt from committed files shows "not logged in this store". The client and the links use the standard library's `urllib` and go through no proxy, since the servers they call run on this machine, or behind a `kubectl port-forward`, and a proxy of the environment would otherwise receive the problems' statements and solutions. The test-set view is a demonstration on frozen test-set problems: it computes no metric and chooses nothing ([ADR 0001](0001-model-selection-protocol.md)).

## Considered options

- **A Flask app of our own**: it would redo what MLflow's server already does (the input signature, the error responses, `/ping`, the container entrypoint that SageMaker runs) and leave the MLflow model format. MLflow's deployment overview still draws Flask, which its scoring server left in 2.21 for FastAPI.
- **`mlflow models build-docker`**: pip resolves the model's `requirements.txt` instead of `uv.lock`'s pins, and its template keeps pip's cache in a layer, about 12 GB for `f2llm_late_fusion` on a disk with about 16 GB free.
- **Weights mounted at run time** (a volume, a PVC, SageMaker's S3 model data): each platform would need its own way to bring 1.2 GB of weights, and an image alone would not serve.
- **Two images per method, one for the CPU and one for the GPU**: a `+cpu` torch wheel would depart from `uv.lock`'s pins, and the two images could drift apart.
- **Keeping the F2LLM-only `CODEFORCES_F2LLM_DEVICE`**: the ModernBERT methods would read no variable, a deployment would need one variable per method family, and a variable silently ignored is the failure to avoid.
- **Tags only, as the logged wrapper returns them**: the response would not show how close each score came to its per-tag threshold, nor what an API answer cost.
- **The logged model of the MLflow store**: its id exists only in the store of one worktree, rebuilt from committed files with new ids, and it ships neither `codeforces_tags` nor the weights.
- **A Streamlit container in the compose file**: the app reads the dataset and the committed frozen rows from the user's checkout; in a container it would need both mounted, for a demonstration that one command starts locally.
- **`MlflowClient` in the app**: the app would import mlflow, set its environment and open the sqlite store beside the UI that already serves it; the links need the UI anyway, and REST over the standard library keeps the app's group to streamlit.
- **A fully live notebook 12, or an explanatory one**: re-executing a fully live one would need Docker, a GPU, kind and AWS; an explanatory one would show no real output. It serves locally, live, and quotes the Docker, Kubernetes and SageMaker runs as recorded outputs.
- **A real SageMaker endpoint, or manifests only**: the first pushes about 8 GB and bills by the hour for a check that the container contract run locally gives; the second would prove that nothing runs.

## Consequences

- The served model is built from the committed folder, never the store: any checkout with the folder and the weight caches packages the same model, and the logged models, `TaggingMethodModel` and `load_logged_method` are unchanged. The deployment entry file is a second wrapper beside the logged one (`tracking/pyfunc_model.py`): both load a method folder through `load_method`, and only the served one returns scores, thresholds, cost and failure.
- The image and `serving.local` reproduce `load_logged_method`'s guards without calling it: pickle loading is off (the image sets every pair of `config.MLFLOW_ENV_DEFAULTS | config.MLFLOW_ENV`), `package` checks that the model's loader is `mlflow.pyfunc.loaders.code_model`, the model carries explicit requirements and no `uv.lock`, and no bytecode is written (`PYTHONDONTWRITEBYTECODE=1`), so no cached `.pyc` runs instead of the reviewed `.py`.
- Inside the image and under `serving.local`, the package runs from `model/code`, so `config.PROJECT_ROOT` is the model folder (`/opt/ml/model` in the image, `build/serving/<name>/model` under `serving.local`), where the weight caches it would read by default do not exist: the image and `serving.local` point `CODEFORCES_PRETRAINED_DIR` and `CODEFORCES_TRAINED_DIR` at the staged weights, and the method folder comes from the model's artifacts.
- `mlflow.models.container._serve` is private API: `uv.lock` pins MLflow, and `tests/test_deploy_files.py` compares the `ENTRYPOINT` with the line MLflow writes, so an upgrade that changes it fails a test. MLflow's entrypoint exits with status 0 when the server dies (`cuda` without a GPU, say), so compose sets no restart policy; Kubernetes restarts the pod whatever the status.
- The model server has no authentication: compose publishes it on `127.0.0.1` only, Kubernetes behind a ClusterIP Service, SageMaker behind IAM.
- `serving up` runs the whole local path in one terminal, so that a method can be tried without three shells: it checks everything before it starts anything, starts the model server (compose, or `serving.local` with `--local`), the MLflow UI and the Streamlit app on `127.0.0.1`, and stops all three, in reverse order, on Ctrl-C or once one of them dies; it adds no platform and changes no image, and the app stays a client on the user's machine.
- The Streamlit test-set view chooses nothing (ADR 0001): it shows one problem's live prediction beside its frozen row and its true focus tags, never a score over the test set, and the methods keep being compared on dev.
- API methods take exactly one problem per request, `smoke` checks only local methods, and API methods are not deployed to SageMaker.
- Images are large, about 8 GB for `f2llm_late_fusion` and 1 GB for `tfidf`: once a build succeeds, `build` removes the method's older images (never another repository's, nor one a container still uses), BuildKit's cached build contexts and the staged weights; `--keep-previous` keeps them. The prune (`docker builder prune --filter type=source.local`) drops every cached build context on the host, not only this method's: nothing is lost, since they are caches, and a later build sends its context again.
