# Every prompt version of an API method is one versioned YAML file in git, mirrored in MLflow's prompt registry

The words an API method sends were spread over Python literals and loose files: the Jev convention, question and eight tag definitions were literals of `methods/typesafe_jev/settings.py`, and the zero-shot prompts were two `.j2` templates and one `.json` schema, with nothing on disk saying which version of which prompt a file was. Each prompt version now lives in one file of its method's package, `templates/<name>.v<N>.yaml`, that holds its own `name` and `version` beside the keys its method reads: `jev-tags.v1.yaml` holds the convention, the question (a Jinja2 template, filled with the tag) and the tag definitions of [ADR 0007](0007-api-score-methods-share-the-llm-toolkit.md)'s two methods; `code2tag.v1.yaml` and `descode2tag.v1.yaml` hold a zero-shot setting's template for the `text` output format, and their `.v2.yaml` the same template with the answer schema (`response_format`) for `json`, the versions each prompt already had in the registry. One reader, `codeforces_tags.prompt_files` (`read_prompt_file`), parses a file with YAML's safe loader, which builds only plain data, refuses a key written twice at any depth, checks that the file's `name`, `version` and path agree and that its top-level keys are exactly the ones its method reads, and returns its text with the sha256 of its bytes. The templates inside stay Jinja2, rendered by `templating.py` as before.

Each version is registered in MLflow's prompt registry: registered once, in its package's order, then only checked on every store (`tracking.prompts.register_prompt_versions`, with `register_prompts` for the prompted methods and `register_jev_prompt` for the Jev methods), each version tagged with its content hash (and, for `jev-tags`, the file's sha256 and `sha256_json(SETTINGS)` as `settings_sha256`), and linked to the method runs and logged models that read it (a zero-shot method's through the `prompts:/<name>/<version>` its run record pins and `log_method` passes to its logged model, a Jev method's by `link_jev_prompt`, through `link_prompt_version`). The registry mirrors and gates nothing: git and the answers files stay the gates of [ADR 0003](0003-api-methods-are-fixed-reference-models.md), and no command reads a version, an alias or a tag to decide whether to send a request.

The move changed no byte of any request, recipe or prompt content hash, and the tests prove it from committed values. Every committed request hash rebuilds: each Jev request is still the same wire bytes (`JevRequest.sha256`; the questions' digest is pinned as computed before the move), and each zero-shot request the same `LlmRequest.sha256`, since the prompt files hold the approved templates byte for byte and the schema in its own key order (both pinned by their sha256 from the old `.j2` and `.json` files). The Jev `SETTINGS` mapping keeps its five keys and still hashes to `8eda74ec4c3f3f8e38c952ac82b334c8888b2e08b0fe4ad6f1df1ebae2a2c7b7`, so both `recipe_sha256` values and the `settings_sha256` of each `jev.json` are unchanged; the four zero-shot `PROMPT_CONTENT_SHA256` pins and recipes are unchanged. The offline `verify` of each of the six methods (`python -m codeforces_tags.llm verify`, `python -m codeforces_tags.methods.typesafe_jev verify`) rebuilds every request of every committed answer against its line's hash and re-derives every frozen file, with no request and no key.

Four rules keep the frozen methods as they were frozen.

- **The Jev question is recorded in its frozen form.** The prompt file writes the question as a Jinja2 template, but the recipes hashed it in the `str.format` form, `{tag}`: `SETTINGS` keeps that form (the template rendered with `tag="{tag}"`), so the recipes still hold.
- **Frozen zero-shot folders keep their historical paths.** The four `prompted.json` files name the `.j2` and `.json` paths the methods were frozen with, which no longer exist: they say where the prompt was read, not what it is, the folder holds the prompt itself, and its content hash pins it. A folder is never rewritten to follow the move.
- **Frozen Jev run records keep `prompts: []`.** They were frozen before the prompt registry held `jev-tags` and are never rewritten; they are linked to its version 1 through the `settings_sha256` tag that their `jev.json` holds and through the MLflow links of each method's run and logged model. A run record made from now on pins `prompts:/jev-tags/1`.
- **A new wording is a new file version, read by new methods.** A file never changes after its first dev request, since every word is in each request's hash. A new Jev wording is `jev-tags.v2.yaml`, added to `prompt_versions()`; the zero-shot prompts' versions are already their output formats, so a new zero-shot wording is a new prompt name, as ADR 0003 says. Either way it is read by new methods under new names, with new paid requests.

## Considered options

- **Python literals (the status quo for Jev)**: the words sat among the code that sends them, with no version of their own, so a reader could not point at one prompt version, and the registry would have held a copy rebuilt from code rather than the reviewed text.
- **JSON files**: also plain data, but long definitions need escaped newlines and quotes, and JSON holds no comment to say what a file is and that it is frozen. YAML's folded scalars keep the words readable, and the safe loader with duplicate keys refused keeps it as strict as JSON.
- **One YAML file per prompt name, with its versions inside**: a new version would edit a file that frozen methods read, so a stray edit to version 1 would sit in the same diff as version 2. One file per version is only ever added, and git shows a frozen version untouched.
- **MLflow's prompt registry as the source of truth**: the store is gitignored and local, can be edited in the UI and is rebuilt from committed files ([ADR 0002](0002-method-folders-and-mlflow-wrapper.md)); a gate there is the one ADR 0003 refused. The registry mirrors the files instead.

## Consequences

A reader finds every prompt version an API method ever sent as one file in git, and the registry shows the same text with the runs and models that read it. Adding a version is adding a file and naming it in its package's list of versions (a zero-shot method's `prompt_family`, `prompt_versions()` in the Jev package's `tracking` module), registered on the next `run` or `score`/`freeze`. Changing a frozen file fails the hash pins in the tests before `run` refuses its answers: the tests pin each Jev request's bytes and the sha256 of `jev-tags.v1.yaml` itself, comments included, since that hash is the `content_sha256` tag that every store checks; a zero-shot file's template and schema are pinned by their sha256, and its registered version by the method's content hash, which its comments do not enter. Every API method's module imports the prompt-file reader, so `pyyaml` is a default dependency and in each API method's registry requirements: a zero-shot method predicts from the prompt its folder holds (`prompted.json`), and the Jev methods read `jev-tags.v1.yaml` when their `settings` module is imported. The frozen methods' historical traces stay as they were frozen (the `.j2` paths of the zero-shot folders, the empty `prompts` of the Jev run records), and nothing rewrites them, so the move costs no paid request and leaves `assets/` byte for byte.
