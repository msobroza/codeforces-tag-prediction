# API methods are fixed reference models, enforced by their answers files

A method that sends paid requests (an API method, `MethodSpec.calls_api`) is a prompted method served by the LLM toolkit (`src/codeforces_tags/llm/`). Its prompt template and its JSON schema (one versioned prompt file of its package per prompt version, [ADR 0009](0009-versioned-prompt-files.md)), the problem fields and constants it renders, its tags and its answer-shaping settings (`LlmSettings`: provider, model, reasoning effort, temperature, top_p, maximum output tokens and output format) never change after its first dev request. Each request is hashed over what shapes its answer (`LlmRequest.sha256()`: provider, model, rendered input, schema and schema name, temperature, top_p, reasoning effort and maximum output tokens; the schema as its JSON text in its own key order, since a structured answer writes its keys in the order of the schema's properties), and each answer is appended, as it arrives, to the method's committed `assets/methods/<name>/answers_<part>.jsonl` under that hash. `llm run` sends nothing while a line of either answers file is under another hash than its problem's current request, so a changed prompt can neither reuse an answer nor mix with one: starting over is a new method with a new prompt name, and the old method's files stay as they are. Transport settings (`config.LLM_*` other than the prices: storage, prompt caching, service tier, timeout, retries, concurrency) are in no hash, so changing them invalidates no answer. This extends [ADR 0001](0001-model-selection-protocol.md) to models behind an API.

The APIs have no seed, and the model behind a name can change or retire, so the answers files are the record, not a cache in front of it: every number of an API method is computed from them, offline (its predictions, metrics, tokens and cost by `llm score` and `llm verify`, its bulk throughput by `tracking latency`), and no request is ever sent again to reproduce one. A line holds the request hash, the problem's sample id, the provider's answer with its status, usage, ids and timing, and never a statement or a solution, so the dataset is not redistributed. A line is final once written, failed or not: a request the API refused (`api_error:<status>`), an answer cut off at the token cap or refused by the model scores as the empty tag set and is counted, while a transient error writes no line, and the next `llm run` sends that request again. The files are only appended to: `llm run`, `llm score` and `llm verify` refuse an answers file that lacks or changes a line of one of its committed versions, or of its last one on disk (`provenance.committed_versions`, `store.check_append_only`), so deleting a failed answer's line never has its request asked again. A free-text answer is read by a fixed parser (`parse_text_tags`, `config.TEXT_PARSER_VERSION`), written and tested before the first paid request and never adjusted after results are seen.

Five rules follow.

- **Dev first.** `llm run --part test` refuses until `answers_dev.jsonl` is committed, unchanged against `HEAD`, and holds a line for every dev problem under the current request hashes; `--allow-dirty`, which concerns code, does not lift it, and `llm run --part dev` sends nothing once the test part has answers. The parts are those of the frozen split, `assets/split/split.csv`, which `llm run` and `llm score` require committed and unchanged; the commands take no `--split`, since a split that parked an unanswered dev problem elsewhere would lift the gate. `llm score` records the commit that last changed each answers file.
- **The contamination slice is fixed first.** `llm run` refuses until `assets/slices/self_identifying_solutions.csv` is committed, unchanged and equal to the slice recomputed on the data, so the problems set aside for the contamination check are fixed before any answer is seen.
- **Learning from dev stays out of fold.** A prompted method that uses dev labels (e.g. few-shot examples) gets its dev requests from `cross_requests`: fold k's requests come from the method fitted on the other folds, and every one is recorded in its answers file. Its test requests come from the method fitted on all of dev.
- **Nothing is chosen from test.** The methods compared in one study (e.g. the paper's four zero-shot methods: two settings, two output formats) are fixed before that study's first test request, and any comparison between them (e.g. free text against structured output) is concluded on dev. Their test scores are reported side by side and never used to choose.
- **MLflow mirrors and gates nothing.** `register_prompts` registers a prompt's versions once, in its package's order, then only checks them; run records and logged models pin the numeric version (`prompts:/<name>/<version>`), and the aliases, one per output format, mirror the frozen methods. No command reads an alias, a tag or a run as a gate: git and the answers files are the gates.

## Considered options

- **Asking the API again to reproduce a number**: there is no seed, a model name can point to a new snapshot, and snapshots retire. A second run would be a new sample, paid again.
- **A cache under the gitignored `experiments/`, with the record elsewhere**: a cache nobody reviews can drift from the record. One committed append-only file per part is both: resuming reads it, and every number comes from it.
- **Iterating on a prompt with its dev scores**: the dev scores would be in-sample for the prompt. The paper's prompts are written once; another prompt is another method, frozen with its own answers, and recorded `dev_in_sample` when it was chosen while reading dev ([ADR 0004](0004-tagging-method-framework.md)).
- **Gating the test run with MLflow aliases or tags**: they live in a gitignored store and can be moved in the UI. `committed_unchanged` and the request hashes are checked against git.
- **Hashing the whole request body, transport settings included**: raising a timeout or the concurrency would invalidate every answer.
- **Storing the rendered prompt in each line**: it would commit the dataset's statements and solutions. The request hash pins the prompt without its text, and `llm verify` renders every request again to check it.

## Consequences

An API method is a fixed reference model in ADR 0001's sense: nothing about it is chosen after its first dev request, its dev scores are honest (a zero-shot method learns nothing from dev, and a fitted one is answered out of fold), and its test part is scored once. Whether the CLI may use one is decided as for any frozen method, on dev and under the latency budget (ADR 0004).

Changing a prompt after its first request costs a new method name and new paid requests, which is the point: anyone can check from the committed files alone that no answer was asked under another prompt, `check_frozen_method` holds each committed API method to one answer per problem, and `llm verify` re-derives every number without a request or an API key. An empty MLflow store is rebuilt from the committed answers by `llm score` and the `tracking` commands, with no paid call; only the first run of `tracking latency` sends live requests, outside the answers files and under a cost cap.
