# One framework for every tagging method

Every tagging method, whether it is the tag model, a prompted LLM, a rule-based method or one not named yet, implements the `TaggingMethod` Protocol (`name`, `tags`, `predict(raw_problems)`, `save(folder)`), saves a data-only method folder ([ADR 0002](0002-method-folders-and-mlflow-wrapper.md)), registers one `MethodSpec` line in `METHODS`, and passes `check_tagging_method` in its own tests. Its dev numbers are out of fold whenever it learns from dev labels: `CrossFittedTagThresholds` for a score method, `cross_predict` for a fitted 0/1 method, and [ADR 0001](0001-model-selection-protocol.md) for any tuning, whose frozen results go in `assets/methods/<name>/tuning/` (the tag model's study, which predates the framework, keeps them in `assets/tfidf_baseline/`). The exception is a method marked `dev_in_sample` (below).

Its test part is scored once and frozen with `freeze_predictions`, and its frozen files live in `assets/methods/<name>/` with a run record. It is logged with `log_method`, and timed and evaluated with `tracking latency` and `tracking evaluate`. Its heavy dependencies stay in its own package and dependency groups. It saves no pickle: weights go in safetensors, skops, `.npz` or JSON files.

Five rules follow.

- **Pretrained weights are never in a method folder.** The folder holds `pretrained.json`: `repo_id`, the `revision` commit sha, and each weight file's name and sha256. `load` reads the weights from `config.PRETRAINED_CACHE_DIR` (under the gitignored `experiments/`; `$CODEFORCES_PRETRAINED_DIR` overrides it, read at call time as `read_samples` reads `$CODEFORCES_DATA_DIR`) with `HF_HUB_OFFLINE=1` and `use_safetensors=True`, and checks the hashes. The method package's `fetch` command downloads them once. A logged model whose folder has a `pretrained.json` therefore needs the weight cache on the machine that loads it. Trained weights too large for a method folder follow the same rule, with `trained.json` ([ADR 0006](0006-trained-weight-cache.md)); a bag of fine-tuned fold models is a score method ([ADR 0005](0005-fine-tuned-model-protocol.md)).
- **Dataset text is never in a method folder.** A method that keeps problems (e.g. few-shot examples) stores only their `sample_id`s, with the sha256 of each one's fields. Its `load` reads the texts from the dataset (`read_samples()`, `$CODEFORCES_DATA_DIR`) and checks the hashes, so its folder, like a logged model of it, needs the dataset, as pretrained weights need their cache.
- **Choosing among frozen methods.** Local methods freeze dev and test in one command. A frozen method is eligible for the CLI when it is neither `dev_in_sample` nor `test_informed` ([ADR 0011](0011-platt-lipton-threshold-rule.md)) and the slowest problem of its `latency.csv` takes less than `config.LATENCY_BUDGET_S` (10 seconds, `PROBLEM.md`'s limit for one prediction), and this rule names the eligible method with the best dev out-of-fold macro F1 (`best_dev` in `codeforces-tags methods`). The method the CLI runs by default is chosen among the eligible ones, never on a test score ([ADR 0008](0008-cli-default-method.md)). Every other frozen method is a reference: its test score is reported and never used to choose. A local method's `freeze` sets `method_entries["supersedes"]` itself: the sorted names of the other registered methods of its package (the same `codeforces_tags.methods.<package>` prefix of `MethodSpec.module`; `tfidf` has none) whose `predictions.csv` is `committed_unchanged` when it runs, so sibling methods frozen before either is committed get `[]`. `check_frozen_method` checks that the key exists, and notebooks list the non-empty values. API methods keep [ADR 0003](0003-api-methods-are-fixed-reference-models.md)'s dev-then-test gate.
- **Dev scores read in sample.** Any method, whatever its kind, whose rules or settings were chosen while reading dev data (e.g. a rule-based method) records `method_entries["dev_in_sample"] = true`. It has no out-of-fold dev score, so it is never eligible for the CLI: notebooks label its dev score in-sample, and `log_method` tags its run and logged model `dev_in_sample=true`. A method whose idea, rule or settings came from reading a test score records `method_entries["test_informed"]` as well ([ADR 0011](0011-platt-lipton-threshold-rule.md)): it is never eligible either, its dev rows keep their own label, and its test score is a reference.
- **Composite methods** (stacking over other methods' outputs; `MethodSpec.depends_on` names the bases). Their level-2 out-of-fold rows are not nested: the level-2 model that predicts fold j is fitted on other folds' base rows, which came from base models that saw fold j's labels. This is accepted, and nested cross-fitting is optional. A composite's logged model needs its bases' committed method folders under `config.METHODS_ASSETS_DIR` on the machine that loads it.

## Considered options

- **An abstract base class**: a zero-shot method would need a fake `fit`. `TaggingMethod` is a structural Protocol (the Strategy pattern), and every consumer depends on it.
- **The scikit-learn estimator interface for every method**: an HTTP client is not cheap to clone, and scikit-learn's `n_jobs` would pickle it to its workers. A method that outputs scores follows scikit-learn's estimator contract (`fit`, `decision_function`, `clone()`, written out in the docstring of `CrossFittedTagThresholds`), a PyTorch model wrapped as an estimator included, and gets ADR 0001's cross-fitted thresholds from `CrossFittedTagThresholds`. A new `Scorer` Protocol would only restate that contract.
- **Decorator self-registration, or entry points**: the first runs every method's import for its side effect, the second is made for third-party plugins. A dict of `MethodSpec` lines, one per method and sorted by name, imports a method's module only when it is loaded.
- **Choosing the CLI's method on its test score**: the test set would become a second dev set (ADR 0001).

## Consequences

A new method touches its own package (`src/codeforces_tags/methods/<package>/`, with its own `settings.py`, command and dependency group), one registry line and `assets/methods/<name>/`, so parallel sessions rarely meet in one file. `check_tagging_method` fails a method that breaks the contract in its own tests, and `check_frozen_method` fails a committed method whose files are incomplete or inconsistent with the frozen split.

A frozen method's test predictions are never overwritten by another recipe: `freeze_predictions` refuses, so a changed method is a new model with its own single test score (ADR 0001), not an edit of the old one. The rule's choice is then mechanical, on dev out-of-fold macro F1, the CLI's default is chosen among the eligible methods ([ADR 0008](0008-cli-default-method.md)), and every test score reported beside them is a reference.
