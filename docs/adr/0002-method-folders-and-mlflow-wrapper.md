# Tagging methods are saved as method folders and logged through one MLflow wrapper

Every tagging method saves itself to a method folder: `method.json` (the method's name, the format version and its tags, written by `save_method`) plus the method's own data files. Those are JSON, CSV, `.npy` or `.npz`, skops, safetensors or ONNX files, never a pickle, never an absolute path, never pretrained weights or dataset text ([ADR 0004](0004-tagging-method-framework.md)), and at most 50 MB each and 100 MB in all; trained weights over these caps stay in a local cache that the folder pins by hash ([ADR 0006](0006-trained-weight-cache.md)). A folder loads without MLflow: `load_method(folder)` reads `method.json`, then imports the module that the code's own registry (`METHODS`) names for that method, so a folder never chooses which code runs. MLflow logs the folder through one models-from-code wrapper, `tracking/pyfunc_model.py`, handed to `mlflow.pyfunc.log_model` by its path, with the folder as the artifact `method`, an explicit signature of raw string columns and requirements pinned from `uv.lock`. The run record, which pins what the method was computed from, becomes the logged model's write-once parameters.

A saved method names the code that loads it by import path, so these paths are frozen: `codeforces_tags.preprocessing.pipeline.raw_to_problems` and `codeforces_tags.model.thresholds.CrossFittedTagThresholds` (skops stores the functions and classes of a pipeline by path), and `codeforces_tags.methods.load_method`, `codeforces_tags.methods.METHODS` and `codeforces_tags.tracking.pyfunc_model.TaggingMethodModel` (what the entry file of every logged model runs). Renaming or moving one makes saved method folders or logged models unloadable. skops builds only the types it is told to trust, and each skops method's test pins the exact list.

Seven safeguards keep the wrapper from running code nobody reviewed or logging more than it should, and a prompted method from drifting away from its prompt. Each has a test, and the code cites them by number.

- **Safeguard 1, one sanctioned loader.** `load_logged_method` is the only code that loads a logged method. It points MLflow at the project's store (so a fresh process never writes MLflow's default `./mlflow.db`), turns pickle loading off, checks that the MLmodel's loader is `mlflow.pyfunc.loaders.code_model`, and loads with `sys.pycache_prefix` pointed at a temporary directory: a `.pyc` cached in the store would otherwise run instead of the reviewed `.py`.
- **Safeguard 2, an explicit raw-string signature.** The raw sample inputs and outputs stay JSON strings. MLflow 3.16 returns twice the rows, or pairs rows wrongly, for list columns on a frame indexed by `sample_id`. Every raw column is a required string, so rows go in as `read_samples()` or `select_part` give them, a missing field NaN in a `str` column: a problem typed by hand with `np.nan` alone in a field has a float64 column, which MLflow's schema check refuses until it is cast with `astype({column: "str"})`.
- **Safeguard 3, explicit requirements.** uv auto-detection is off and `method_requirements` pins each requirement from `uv.lock`: otherwise every logged model copies `uv.lock` (990 KB) and lists 173 requirements. A test lists a logged model's files: no `*.pkl`, `*.pickle` or `*.joblib`, no pickle header bytes, no `uv.lock`, no `__pycache__`.
- **Safeguard 4, a prompted method's prompts and answers are pinned** (added with the LLM toolkit, [ADR 0003](0003-api-methods-are-fixed-reference-models.md)). Every prompt renders through `templating.render_string` or `render_template`, one strict Jinja2 environment: a variable the template needs and did not get is an error, nothing is escaped, and a value is never rendered again. MLflow's `PromptVersion.format` is never called: it renders a missing variable as empty text and substitutes again inside values. `register_prompts` registers a prompt's versions once, in the order of its package's `prompt_family` (`text` then `json` for the paper's settings), so a version number names the same prompt on every store, and it refuses a store whose versions differ. Each version holds the settings as a flat `model_config` dict (MLflow's `PromptModelConfig` drops `reasoning_effort`) and a `content_sha256` tag, and is made with `create_prompt_version`, never `register_prompt`, which copies the tags onto the prompt and links it to an experiment from a thread of its own. Run records and logged models pin the numeric version (`prompts:/<name>/<version>`), never an alias. The answers are frozen in committed files, and every number of the method is computed from them.
- **Safeguard 5, dataset-level metrics are logged once.** `log_method` logs each dataset's metrics (`dev-oof`, `test`) once, on the method's logged model, with the sample ids of the split the freeze read. MLflow writes them to the method run too, whose view keeps each key's latest value: `dev-oof` is logged last, so the run shows the selection score, never the test score (ADR 0001). Evaluation runs repeat them only as run metrics without a model id.
- **Safeguard 6, frozen import paths are pinned in one test**: the names the entry file reaches the framework through, plus each skops method's trusted types.
- **Safeguard 7, one place sets MLflow's environment.** `mlflow_env()` sets it from `config.MLFLOW_ENV`: pickle loading off, uv auto-detection off, one evaluation worker and synchronous trace export (sqlite silently loses evaluation rows and traces otherwise), no price catalog fetched, and no job runner in `mlflow server`. MLflow reads two of its variables, telemetry and its hint to coding agents, only when it is imported, so importing `tracking/` or `tuning/` sets those first (`mlflow_env(MLFLOW_IMPORT_ENV)`). A test fails when any other module writes an MLflow variable.

## Considered options

- **An instance of the wrapper, or MLflow's scikit-learn flavor, for every method**: MLflow cloudpickles an instance into `python_model.pkl`, and loading it runs any code it holds. The scikit-learn flavor fits estimators only, not a prompted method or a fine-tuned transformer.
- **A method folder that names its own module**: the folder would choose which code runs when it loads. The registry of the loading code chooses instead, and `load_method` raises on a name that it does not list.
- **MLflow's defaults for requirements, tracing and evaluation**: they copy `uv.lock` into every model, drop evaluation rows and traces on sqlite, and fetch a price catalog from the network (safeguards 3 and 7).
- **The MLflow Model Registry**: it versions deployable models and adds no per-problem view. The ids of the logged models, their dataset inputs and their prompt links already give the lineage.

## Consequences

Moving a frozen path is a migration of every saved method folder and logged model, not a refactor. Loading a logged model runs its entry file, so only this project's models are loaded, and only through `load_logged_method`. A logged model is not always self-contained: one whose folder has a `pretrained.json` needs the weight cache on the machine that loads it (and one with a `trained.json`, the trained cache: ADR 0006), one that reads example texts needs the dataset, and a composite method needs its bases' committed method folders (ADR 0004).

The MLflow store is gitignored. `assets/` is the record, and every write to the store is idempotent and comes from committed files, so an empty store is rebuilt by each method's `freeze` (`llm score` for an API method) and the `tracking` commands without a paid call. A bit-reproducible method's `freeze` re-derives its predictions to check them, so the rebuild refits it and needs the dataset.
