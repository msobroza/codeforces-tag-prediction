# A threshold rule that reads calibrated probabilities, and methods proposed after a test score

Every score method so far turns a tag's scores into 0/1 with the same threshold rule: the F1-maximising threshold, cross-fitted over the five dev folds ([ADR 0001](0001-model-selection-protocol.md)). For the Jev methods, whose scores are probabilities ([ADR 0007](0007-api-score-methods-share-the-llm-toolkit.md)), this rule failed once. The searched method `jev-statement-code-gepa` ([ADR 0010](0010-searched-jev-words.md)) lost 0.025 of test macro F1 against `jev-statement-code`, the command line's default ([ADR 0008](0008-cli-default-method.md)), paired, with an interval of [−0.041, −0.010]; two thirds of that loss came from `probabilities`, whose cross-fitted threshold fell from 0.870 to 0.125.

The cause is on dev, and visible without the test set. The F1 curve of that method's `probabilities` has several almost equal peaks: four runs of cuts lie within 0.01 of its maximum, 0.125-0.145 (F1 0.7602), 0.315-0.325 (0.7600), 0.405-0.435 (0.7518) and 0.735-0.815 (0.7576). So the F1 argmax jumps between them depending on which four folds choose it: GEPA's five fold thresholds are 0.810 and 0.770 (folds 0 and 1) in the high run, and 0.125 (fold 2) and 0.325 and 0.325 (folds 3 and 4) in two of the low ones. Under a group bootstrap of dev, the threshold falls below 0.5 in 68% of resamples for GEPA, and in 13.5% for the frozen `jev-statement-code`. An increasing map of the scores followed by the F1 argmax changes nothing, since it keeps the order of the scores (0 cells differ on either Jev method, as on TF-IDF in notebook 04). A Platt scorer fitted per fold inside `CrossFittedTagThresholds` still collapses on GEPA's folds 2-4, and its final threshold only looks fixed because the highest run (0.7602) stays just above the next one (0.7600).

What fixes it is a rule that reads the calibrated value, not the place of the curve's maximum. On calibrated probabilities the F1-optimal threshold is half the best F1 (Lipton et al. 2014), so the rule uses only the height of the F1 curve, which is stable. **The threshold rule R2 is fixed here, before any new number.** For one tag, on the fitting scores p (Jev's probabilities) and 0/1 labels y:

1. If y has no positive, the threshold is `inf`, as `best_threshold` gives.
2. x = logit(clip(p, 1e-4, 1 − 1e-4)). The clip only binds for a failed answer's 0.0.
3. **Platt:** fit a logistic regression without penalty (`model.platt_lipton.rule_calibrator()`, `C=inf`) on x as its single feature, to convergence (`config.PLATT_SOLVER`, Newton-Cholesky, at `config.PLATT_TOL`, 1e-12), giving the maximum-likelihood slope a and intercept b. scikit-learn's default lbfgs stops near 1e-4 of the gradient, which moved 4 of the twins' 80 fold thresholds by one grid step in a first freeze, so the map is fitted to convergence and a threshold does not depend on when a solver stopped. A slope a ≤ 0 is refused with a `ValueError`.
4. **F1\*:** the F1 of `best_threshold(p, y)` on the same fitting scores, the in-sample maximum. The Lipton cut is q\* = F1\* / 2.
5. **Map back:** the raw threshold is t = expit((logit(q\*) − b) / a). Since a > 0, `expit(a·x + b) ≥ q*` holds exactly when p ≥ t.
6. **Snap to Jev's grid.** Jev's probabilities lie on a 0.01 grid, and a failed answer scores 0.0. The stored threshold is the midpoint below the smallest grid value at or above t, so that predictions on grid scores are those of p ≥ t (a t within 1e-9 grid steps above a grid value, the float noise of expit and logit, counts as that value), the stored number is a short decimal that `verify` compares exactly, and a failed answer is never predicted.

The cross-fitting is that of `CrossFittedTagThresholds`: fold k's thresholds come from the rule fitted on the out-of-fold scores of the other four folds, and the final `thresholds_` from the rule fitted on every out-of-fold score. The rule's settings are `RULE_SETTINGS` in `model/platt_lipton.py` (the name `"platt-lipton"`, the feature `"logit"`, the clip `config.PLATT_CLIP = 1e-4`, `C=inf`, the solver `config.PLATT_SOLVER = "newton-cholesky"` and its tolerance `config.PLATT_TOL = 1e-12` of step 3, the grid `config.SCORE_GRID = 0.01`); they are in each twin's recipe and in its `jev.json`'s settings hash, so a change of any of them is a changed rule, and a new method (below). The clip, the grid, the solver and its tolerance live in `config.py`, since `model/` and `analysis/` both read them (`analysis/` reads the last two through `rule_calibrator()`). The module and this ADR are named after the rule, Platt + Lipton, never after the phrase that the glossary bans. The rule is a subclass of `CrossFittedTagThresholds`, `PlattLiptonThresholds`, which overrides only the threshold choice: the frozen class is never edited, since the tag model's skops file names it ([ADR 0004](0004-tagging-method-framework.md)).

**Two calibrated twins, composites over their bases' answers.** `jev-statement-code-platt` (base `jev-statement-code`) and `jev-statement-code-gepa-platt` (base `jev-statement-code-gepa`) are tagging methods of kind `score` with `calls_api=True` and `depends_on` their base. A twin sends no request and costs $0: it reads its base's committed answers files and `scores.csv` (its scores are the base's probabilities, the same numbers), keeps its base's words, and applies its own thresholds. It has no answers files of its own, so [ADR 0003](0003-api-methods-are-fixed-reference-models.md)'s record stays the base's, and its `latency.csv` and `per_problem.csv` are the base's, copied byte for byte, since a prediction is the same request and each problem's recorded call is the base's. A base is never edited: its frozen predictions, thresholds and recipe stay as they are, and a changed rule is a new method with its own single test score ([ADR 0004](0004-tagging-method-framework.md)). `jev-statement` has no twin: a nested choice run on it while the rule was planned kept R0 in four outer folds of five, and its nested out-of-fold macro F1 (0.726) stayed below R0's (0.729).

**The comparison is declared, and dev only.** Before a twin is frozen, `export --method <twin>` records in the twin's `tuning/`, from the base's committed dev rows alone (it never reads a test row), the out-of-fold macro F1 and per-tag F1 of three rules, each cross-fitted over the five dev folds: R0, the current F1 argmax; R1, Platt then calibrated probability at least 0.5; and R2. It adds each rule's paired difference from R0 with group-bootstrap intervals (`rules.csv`), a nested choice (`nested.csv`: for each outer fold, the rule that wins by cross-fitted macro F1 inside the four other folds, applied to the outer fold fitted on those four) and the stability of every tag's fold thresholds (`stability.csv`). The twin's rule is R2 whatever the comparison shows: the nested choice is reported, never acted on. The dev evidence, out of fold, as the committed records hold it (the converged Platt map of step 3; the first freeze's lbfgs map gave the GEPA twin 0.736, +0.006 [−0.003, +0.015]):

| Method | R0 (current) | R1 (Platt + 0.5) | R2 (Platt + Lipton) |
|---|---|---|---|
| `jev-statement-code` | 0.729 | 0.722 | **0.738** (+0.009 [+0.001, +0.017]) |
| `jev-statement-code-gepa` | 0.730 | 0.721 | 0.737 (+0.006 [−0.002, +0.015]) |

The nested choice picks R2 in every outer fold for both methods, so choosing among the three declared rules adds no optimism (what else was chosen while reading dev is said below, under `dev_in_sample`), and for GEPA's `probabilities` no dev problem depends on which four folds chose the threshold under R2, against 41 under R0. The benefit claimed is stability. The gain in macro F1 is small, and for the GEPA twin its interval includes 0.

**The twins are `test_informed`.** The idea of this rule came after the test drop of `jev-statement-code-gepa` was read (notebook 10, commits `8b9c456` and `5a8366b`). ADR 0001 keeps the test set for one score per model and chooses nothing from it. The rule was evaluated on dev, but a method that exists because a test score was read cannot show that the test set did not shape it. So each twin records `method_entries["test_informed"]` in its run record, with the notebook, the commits and a note (`settings.TEST_INFORMED`), and `log_method` tags its run `test_informed=true`. `cli_methods._eligible` returns false for a method that holds the key, as it does for `dev_in_sample` (ADR 0004): `codeforces-tags methods` lists both twins as not eligible, the default stays `jev-statement-code` and `best_dev` stays `descode2tag-json` ([ADR 0008](0008-cli-default-method.md)). Each twin's test score is scored once, after its dev rows are frozen, reported beside its base and the other methods, and never used to choose. The key is general: any later method whose idea, rule or settings came from reading a test score records it.

**`dev_in_sample` follows the base.** `jev-statement-code-platt` records `dev_in_sample: false`: its words are the frozen method's, written before the first request ([ADR 0007](0007-api-score-methods-share-the-llm-toolkit.md)), and everything the rule fits (the Platt maps, F1\* and the thresholds) is fitted on the other four folds, so its dev rows are out of fold. `jev-statement-code-gepa-platt` records `dev_in_sample: true`, inherited from its base, whose words were chosen on dev folds 1-4 (ADR 0010); its honest dev comparison with its base stays the held-out fold 0. What was chosen while reading dev is more than the nested choice measures. R2 was proposed after the dev F1 curves and the test drop of `jev-statement-code-gepa` were read; R0, R1 and R2 were then declared, before `export` computed the record; other candidates were tried on dev while the rule was planned (a per-fold Platt scorer, which changed no prediction); and `jev-statement` got no twin because a nested choice on its dev rows kept R0. So the nested choice measures only the choice among the three declared rules, and R2's out-of-fold dev gain (+0.009 for `jev-statement-code-platt`) is somewhat optimistic beyond what it measures. `dev_in_sample` keeps the meaning that ADR 0004 gives it, dev rows that are not out of fold: each dev row of `jev-statement-code-platt` is still predicted by thresholds fitted on the other four folds, without its label, so its flag stays false, and this paragraph and `test_informed` disclose what was chosen on dev.

## Considered options

- **The naive per-fold Platt scorer**: a Platt map fitted per fold inside `CrossFittedTagThresholds`, then the F1 argmax. An increasing map keeps every prediction (0 cells differ), and on GEPA's folds 2-4 the argmax still jumps between the peaks; its final threshold looks fixed only because the highest run of the curve stays just above the next one (0.7602 against 0.7600), which is luck.
- **A smoothed F1 curve**: a smoothing narrow enough to keep the curve's shape leaves several almost equal maxima, the outer ones 0.63 of threshold apart, and one wide enough to merge them no longer describes the curve. It cannot bridge peaks that far apart.
- **Platt and a fixed 0.5**: the accuracy rule is not the F1 rule. It loses macro F1 on both methods (0.722 and 0.721, against 0.729 and 0.730 for the current rule).
- **Fresh paid answers for the twins**: Jev has no seed, and its sampling noise would confound the paired comparison with the base, so a difference in dev F1 could be the new sample, not the rule. Reading the base's answers costs $0 and keeps the comparison on the same numbers.
- **`dev_in_sample` for `jev-statement-code-platt`**: it would mislabel rows that are honestly out of fold, and it would give dev as the reason for the twin's ineligibility when the reason is the test score.
- **Replacing the rule of a frozen method**: `freeze_predictions` refuses to overwrite a method's test predictions (ADR 0004), and a changed rule would give the default method a second test score. A twin is a new name with its own single one.

## Consequences

- The twins cost nothing: no request, no key. Freezing them, their latency and the rebuild of the local MLflow store from committed files (11 methods, about 3.5 hours, every dev evaluation before any test one) are free runs.
- A reader finds in the committed files the rule, the base files it was computed from (their sha256 and commits in `tuning/params.json`, which `freeze` and `verify` check), the three rules' dev scores, the nested choice and the stability of the thresholds, all before the twin's test part is scored. Each base file must keep that sha256 and, as its last commit, that commit: a change and its revert give back the bytes, not the commit, so a base file changed after its twin's export means a new twin.
- The twins' test scores are references, reported once and labelled as such: the idea came after a test score was read, so they join no choice. If the notebook finds no detectable difference from the base on dev, it says so.
- A twin's logged model, like its base's, sends a paid request at predict time and needs the SDK and a key (ADR 0007); only its thresholds differ.
- Another rule, or the same rule on another base, is another method under another name, with its own `tuning/`, under this protocol. `jev-statement` keeps the current rule.
