# A method whose API answers probabilities is a score method, on the LLM toolkit's answers files

TypeSafe's Jev model answers a question with a probability. The two methods of `src/codeforces_tags/methods/typesafe_jev/`, `jev-statement` (it reads the statement) and `jev-statement-code` (the statement and the solution), send it one question per focus tag in one request. Each is a Noul question: it asks whether a statement holds, here "would Codeforces put this tag on this problem", and says in its criteria what counts as a yes and as a no, with the tag's definition (the glossary's tag definition). The methods are therefore of kind `score`, not prompted methods that read a tag set from text: Jev's probabilities are their scores, and `CrossFittedTagThresholds` wraps a scorer that learns nothing (`JevProbabilities` returns the probabilities it is given). A dev problem's tags thus come from thresholds chosen on the other four folds, as for the TF-IDF and ModernBERT models ([ADR 0001](0001-model-selection-protocol.md)), and the test part is scored once, with thresholds chosen on all of dev. No request is asked again to get them: the dev scores are the answers themselves. A fixed 0.5 threshold is only a calibration check in notebook 08, never a registered method.

They are also API methods, so they keep every guarantee of [ADR 0003](0003-api-methods-are-fixed-reference-models.md), on the toolkit's own files and functions. Each answer is an `LlmAnswer` line, with the eight probabilities in `output_text` in `FOCUS_TAGS` order, appended to the committed `assets/methods/<name>/answers_<part>.jsonl` under its request's hash: the sha256 of the exact bytes the SDK sends (the state, the pinned model `jev-1.13.0`, never the alias `jev-latest`, which can move, and the eight questions, in the SDK's key order). A changed word of a definition, another model, another state or another order of keys is therefore another hash. The transport settings (timeout, retries, concurrency, cost cap) are in no hash. A line records the model that answered, and `run`, `freeze` and `verify` refuse an answer from any other model; `response_id` and `request_id` both hold the `x-typesafe-request-id` header, TypeSafe's only id. The package reuses the toolkit's store (`llm.store`), git helpers (`provenance`), cost functions (`llm.answers`) and latency timing (`tracking latency`) unchanged, and has commands of its own (`render`, `run`, `freeze`, `verify`), with the toolkit's gates and messages, because the toolkit's commands serve only the methods of kind `zero_shot` and `fitted` and read a tag set from text. A request the API refuses (400, 422) and an answer that is not a probability from 0 to 1 for every tag are final lines, and a failed answer scores 0.0 on every tag and is counted; a timeout or a rate limit that outlasts the SDK's retries writes no line, and the next `run` sends that request again.

Four rules follow.

- **Dev first, and every method of the package first.** `run --part test` refuses until the dev answers of both methods are committed, unchanged and complete, and `run --part dev` sends nothing once the method's test part has answers. The frozen split and the self-identifying slice are fixed before any request, as in ADR 0003. So neither method can be chosen, changed or dropped after a test answer exists.
- **The words are written once.** The convention, the question and the eight tag definitions are written from Codeforces' conventions without reading a dev problem or an answer, and are frozen before the first request, in the versioned prompt file `templates/jev-tags.v1.yaml` ([ADR 0009](0009-versioned-prompt-files.md)): they are in every request's hash and in the recipe of both methods, so neither method is `dev_in_sample`. A changed word after the first dev request is a new method under a new name, with new paid requests.
- **The input is concluded on dev.** The two methods ask identical questions and differ only in the state, so whether the solution helps is a paired comparison on dev. Their test scores are reported side by side and never used to choose.
- **Every number is derived offline.** `freeze` computes the predictions, the scores, each problem's call and every metric from the two answers files, and `verify` computes them again with no request, no key and no SDK; a second `freeze` only checks.

## Considered options

- **A TypeSafe provider inside `llm/providers/`**: a provider's contract renders a prompt and returns text that a fixed parser reads as a tag set, while Jev takes a state and eight questions and returns eight numbers. The runner, the parsers and the commands would all need a second kind of answer.
- **A second, compact answers format**: `check_frozen_method`, `llm.store` and every reader of the toolkit read `LlmAnswer` lines only, so a second format would need its own copy of each check.
- **An uncommitted cache of the answers**: it would break "the answers files are the record" of ADR 0003, since a cache nobody reviews can drift from what was asked.
- **A fixed 0.5 threshold**: nothing says an LLM's probabilities are calibrated, and a threshold chosen on the dev problems it is scored on would be in sample ([ADR 0001](0001-model-selection-protocol.md)). Cross-fitted thresholds are the protocol of every score method, and notebook 08 measures the calibration instead of assuming it.

## Consequences

Each method is a fixed reference model in the sense of ADR 0001 and ADR 0003: nothing about it is chosen after its first dev request, its dev scores are out of fold, and its test part is scored once. Whether the CLI may use one is decided as for any frozen method, on dev out-of-fold macro F1 and under the latency budget ([ADR 0004](0004-tagging-method-framework.md)); a prediction is one paid request, so `tracking latency` times 50 live requests under a cost cap.

A logged Jev model sends a paid request at predict time: its method folder holds `jev.json` (the method's name, the model, the hash of the settings and the thresholds) and no answers, so a loaded method needs the SDK, a key and the network, and asks Jev again, which gives a new sample. The frozen numbers are those of the answers files, and `verify` re-derives them without a request. A changed definition, question or model costs a new method and new requests (about 2,500 input tokens each, about 0.50 USD per method for the 4,982 problems at Jev's price on 2026-10-08), which is the point. `check_frozen_method` holds every committed folder of `assets/methods/` to one answers line per problem, so the answers commits stay local until `freeze` has written the other frozen files, and all of them are pushed together.
