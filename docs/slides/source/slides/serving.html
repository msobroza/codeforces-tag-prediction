A frozen method also runs as a model server: MLflow's own, in one Docker image per method (ADR 0012). The image is built from the committed method folder only, never from the MLflow store: an MLflow model saved from code, the requirements pinned from uv.lock and installed with hashes, and the weights copied and hashed again. Inside, nginx answers on port 8080 in front of MLflow's server, one prediction at a time, offline, with pickle loading off; one environment variable picks the CPU or the GPU at deploy time, so the same image runs on both. The same image runs on Docker Compose, published on localhost only; on Kubernetes, with kustomize overlays for CPU and GPU behind a ClusterIP service; and on SageMaker through aws CLI scripts. There is no authentication or TLS inside the image: localhost, the cluster or IAM keep it private. Clients all share one small client: a Streamlit app, a smoke test that checks 20 test problems against the frozen predictions, and links from the app to the method's run and prompt versions in the MLflow UI. What has really run so far: tfidf, a 906 MB image, under Docker and on a local kind cluster, on the CPU; and f2llm_late_fusion, a 7.89 GB image, under Docker, on the CPU, 3.40 seconds at the median over 20 test problems, and under the GPU profile, 0.148 seconds at the median, holding 2.4 GB of GPU memory. A GPU Kubernetes node, SageMaker and the API methods are written and tested offline but not yet run.
