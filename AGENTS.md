# AGENTS.md

These are the instructions given to the coding agents that built this project (Claude Code reads `CLAUDE.md`; Codex and other agents read `AGENTS.md`), kept as the rules of its development workflow.

Multi-label tag prediction for Codeforces algorithmic exercises (xCodeEval subset, 4,982 distinct exercises).

[`PROBLEM.md`](PROBLEM.md) is the spec. Read it before any decision on scope, features, metrics, or goals.

[`docs/xcodeeval-paper-notes.md`](docs/xcodeeval-paper-notes.md) distills the source paper (arXiv 2303.03004). Read it before working on the dataset schema, tag distribution, splits, metrics, or baselines.

[`CONTEXT.md`](CONTEXT.md) fixes the domain words (problem, statement, solution, focus tag, feature block, fold, out-of-fold score, cross-fitted threshold): use them in code, notebooks and slides. [`docs/adr/`](docs/adr/) records the decisions that are hard to reverse, such as how models are chosen and when the test set is scored ([ADR 0001](docs/adr/0001-model-selection-protocol.md)), how tagging methods are saved and logged ([ADR 0002](docs/adr/0002-method-folders-and-mlflow-wrapper.md)), how a method that calls an API stays fixed ([ADR 0003](docs/adr/0003-api-methods-are-fixed-reference-models.md)), what every tagging method must do ([ADR 0004](docs/adr/0004-tagging-method-framework.md)), how a method whose API answers probabilities is scored on the toolkit's answers files ([ADR 0007](docs/adr/0007-api-score-methods-share-the-llm-toolkit.md)), which method the command line runs by default ([ADR 0008](docs/adr/0008-cli-default-method.md)), where the words of an API method's prompts live: one versioned YAML file per prompt version, mirrored in MLflow's prompt registry ([ADR 0009](docs/adr/0009-versioned-prompt-files.md)), how Jev's words may be searched, as a new method read in sample ([ADR 0010](docs/adr/0010-searched-jev-words.md)), how a threshold rule that reads calibrated probabilities is applied, with the methods proposed after a test score ([ADR 0011](docs/adr/0011-platt-lipton-threshold-rule.md)), and how a tagging method is served over HTTP from its committed folder ([ADR 0012](docs/adr/0012-serving-tagging-methods.md)). Read both before changing the model, its evaluation or how it is chosen, and before adding or serving a tagging method.

## Requirements

Every choice needs a reason that can be stated and checked, in the approach as in the code.

- **Task**: multi-label classification. Inputs include `prob_desc_description` and `source_code` (Python solution); any other dataset field is fair game.
- **Focus tags**: `math`, `graphs`, `strings`, `number theory`, `trees`, `geometry`, `games`, `probabilities`. Other tags are noisy and may be dropped.
- **Metrics**: report per-tag scores as well as aggregates, to show which tags predict best.
- **CLI**: one Python module with `predict` and `evaluate` on a test dataset, plus the training code if the model is learned: `codeforces-tags` (`cli.py`, under Commands).
- **Latency**: a single-example prediction finishes in under 10 seconds.
- **Slides**: approach, metrics and next steps (`docs/slides/`).

## Code style

- **Docstrings**: Google style (`Args:`, `Returns:`, `Raises:`) on every public function, enforced by ruff's `D` rules.
- **Simplicity**: prefer small functions with plain names over clever one-liners. CI fails when a function of the package goes above radon's grade B (cyclomatic complexity 10), and when any function, tests included, goes above 10 as ruff's `C901` counts it (radon also counts boolean operators, comprehensions and asserts, so a test is held to ruff's count only).
- **Shared code**: anything reused by a second notebook or by the model moves to `src/codeforces_tags/`, with a test.
- **Frozen import path**: skops saves the types of a tag model by their import path: the functions of `model/features.py` (`statement_text`, `normalise_statement`, `code_tokens`, `sample_io_cues`), `raw_to_problems` and `CrossFittedTagThresholds`. Renaming one of them, or moving it to another module, makes saved tag models unloadable, and so does moving `model/tag_model.py`, whose module-level `load` the registry names. `STORED_TYPES` (`model/tag_model.py`) lists them, the only types `load` trusts, and a test pins it to what skops reports. The frozen F2LLM fusions depend on import paths too: skops stores `ScoreFusion` (`methods/f2llm/estimators.py`) in `f2llm_late_fusion`'s `model.skops`, and the `model/features.py` functions in both fusions'; `TRUSTED_TYPES` (`methods/f2llm/method.py`) lists each method's types, and a test pins it.
- **MLflow's import-time settings**: `import mlflow` decides once whether to start its telemetry client and print a hint to coding agents, from `config.MLFLOW_IMPORT_ENV`. So a package whose modules import mlflow at module level calls `mlflow_env(MLFLOW_IMPORT_ENV)` in its `__init__.py`, as `tracking/`, `tuning/`, `llm/` and `serving/` do, and `tests/conftest.py` imports `codeforces_tags.tracking` and imports mlflow only inside its fixtures. A fresh-interpreter test fails any `__main__.py` that lets MLflow start telemetry or print its hint, and every test fails once the session has opened a connection outside localhost.
- **Heavy imports stay off the prediction path**: ruff's `TID253` fails CI on a module-level import of optuna, mlflow, gepa, matplotlib, seaborn, openai, typesafe_sdk, playwright or the Claude Agent SDK. The rule is switched off as a whole for `analysis/`, the tuning command (`tuning/search.py`, `tuning/tracking.py`, `tuning/__main__.py`), `tracking/`, the LLM toolkit's command (`llm/__main__.py`), each method's `__main__.py`, `tracking.py` and `tuning.py`, the TypeSafe search's commands (`methods/typesafe_jev/search_commands.py`), the serving package's deployment entry file, packaging and commands (`serving/entry.py`, `serving/package.py`, `serving/__main__.py`), the tests, the notebooks and the figure render tools (`notebooks/figures/*.py`) (`per-file-ignores` in `pyproject.toml`). The core and other methods never import a method's heavy libraries (e.g. torch), and a method's prediction path never imports mlflow, optuna or gepa (fresh-interpreter checks: `check_tagging_method` for a method, a test for the core). A lazy import (inside a function) carries `# pylint: disable=import-outside-toplevel`. A provider's SDK (e.g. openai) is imported only inside its adapter's `ask`, in `llm/providers/<provider>.py`, which also disables `import-error`: CI installs no SDK. TypeSafe's SDK is imported only inside `jev_session`, in `methods/typesafe_jev/client.py`, with the same two disables. In the same package, gepa is imported only by `tuning.py`, and `search_tracking.py` imports mlflow only inside the functions that log, once `use_store` has set MLflow's environment, and `tracking.py` (the prompt `jev-tags` in the registry) reaches it through `codeforces_tags.tracking.prompts`, whose package sets MLflow's environment first; `search_commands.py` and `__main__.py` reach them through these. Of `serving/`, only `entry.py`, `package.py` and `__main__.py` import mlflow: `local.py` and `stack.py` run MLflow's command line in a subprocess, and `mlflow_links.py` talks to MLflow's REST API with the standard library, so the Streamlit app (`apps/streamlit_app.py`, outside `src/`, which imports streamlit and altair at module level) loads none of it (`tests/serving/test_app_files.py`). The command line (`cli.py`, `cli_methods.py`, `__main__.py`) imports none of these libraries at module level, nor anything of `llm/`, `tracking/` or `tuning/`, which set MLflow's environment: a method's own modules load only once `resolve_method()` has passed (fresh-interpreter tests in `tests/test_cli.py`).
- **No pickle**: loading a pickle runs any code it holds. Save in formats that hold only data:
  - tables: CSV or JSON (`pyarrow` comes with mlflow, in the `modeling` group, but the project does not write Parquet);
  - arrays: `np.save` / `np.savez` (`np.load` refuses pickles by default); sparse matrices: `scipy.sparse.save_npz`;
  - scikit-learn models: `skops.io`, which builds only the types you trust (list them first with `get_untrusted_types()`), or ONNX (`skl2onnx`, run with `onnxruntime`). A linear model can also be saved as its parameters: the vocabulary in JSON, the weights in `.npz`;
  - neural network weights: safetensors.

  Even then, load only files this project produced. Ruff's banned-api rule (`TID251`) fails CI on `pickle` (and `_pickle`), `joblib`, `dill`, `cloudpickle`, `shelve`, `pd.read_pickle` (and `pandas.io.pickle`), `torch.save` and `torch.load` (and their `torch.serialization` names; both pickle: save weights with safetensors). It cannot see `df.to_pickle()` or `np.load(allow_pickle=True)`, so avoid them too; `check_method_folder` refuses an `.npy` or `.npz` that holds an object array, which only `allow_pickle=True` loads. `.gitignore` keeps `*.pkl`, `*.pickle` and `*.joblib` files out. Leave scikit-learn's `n_jobs` unset: joblib would write pickle files to pass data to its workers. MLflow logs a tagging method only through the models-from-code wrapper `tracking/pyfunc_model.py`, never through autolog; no code calls `mlflow.autolog` or `mlflow.openai.autolog`; `tracking/environment.py` sets `MLFLOW_ALLOW_PICKLE_DESERIALIZATION=false`.

## Tagging methods

A tagging method turns raw problems (rows of `read_samples()`) into 0/1 tags. It implements the `TaggingMethod` Protocol (`name`, `tags`, `predict(raw_problems)`, `save(folder)`), saves a data-only method folder (`method.json` plus its own files, loadable without MLflow) and registers one `MethodSpec` line in `METHODS` ([ADR 0002](docs/adr/0002-method-folders-and-mlflow-wrapper.md), [ADR 0004](docs/adr/0004-tagging-method-framework.md)). Its kind says how dev gets honest predictions: a score method wraps a scorer in `CrossFittedTagThresholds`, a fitted 0/1 method uses `cross_predict`, a zero-shot method learns nothing from dev, and any other method is kind `other`. Its `freeze` command writes `assets/methods/<name>/` once (`predictions.csv`, `scores.csv` for a score method, `run_record.json`, the method folder) and a second run only checks it; `log_method` mirrors the frozen method to MLflow, `tracking latency` times it and `tracking evaluate` puts every problem's predictions in MLflow, all from committed files, so an empty store is rebuilt without a paid call (a bit-reproducible method's `freeze` re-derives its predictions to check them, so it refits and needs the dataset). `check_tagging_method` is the executable contract that every method's tests call and `check_frozen_method` checks each committed `assets/methods/<name>/`; these import paths are frozen, because saved method folders and logged models name them: `codeforces_tags.preprocessing.pipeline.raw_to_problems`, `codeforces_tags.model.thresholds.CrossFittedTagThresholds`, `codeforces_tags.methods.load_method`, `codeforces_tags.methods.METHODS` and `codeforces_tags.tracking.pyfunc_model.TaggingMethodModel`.

### Adding a tagging method

1. **Package.** Create `src/codeforces_tags/methods/<package>/` with `settings.py` (the method's settings), the method module (a class implementing `TaggingMethod` and a module-level `load(folder)`), `__main__.py` (`freeze`, `verify`, and any `train`, `tune`, `export` or `fetch` command; `tune` and `export` call `tuning.py`) and, if it tunes or logs training curves, `tuning.py` (its Optuna objective and study, journal at `experiments/<name>/optuna.jsonl`) and `tracking.py`. There is no shared tuning runner: each method that tunes writes its own `tuning.py` (exempt from `TID253`) and freezes its results in `assets/methods/<name>/tuning/` (`params.json`, `trials.csv`, `out_of_fold.csv`; the tag model's study, which predates the framework, keeps them in `assets/tfidf_baseline/`); its recipe reads `tuning/params.json`, and its objective is the out-of-fold macro F1 of `CrossFittedTagThresholds(make_estimator(trial), refit=False)` or of `cross_predict`. `methods/label_prior/` is the worked example. A fine-tuned method's study trains on four dev folds and scores the fifth, and its fold models are trained once with the chosen configuration (`methods/modernbert/`, [ADR 0005](docs/adr/0005-fine-tuned-model-protocol.md)). A prompted method served by the LLM toolkit's commands needs no `__main__.py` (LLM toolkit below).
2. **Kind.** A score method wraps an estimator that follows the score-estimator contract (written out in the docstring of `CrossFittedTagThresholds`) in `CrossFittedTagThresholds`, and implements `ScoreMethod` (`scores(raw_problems)`: the `decision_function` of its fitted `CrossFittedTagThresholds`, as a frame indexed like the input; `predict_from_scores(scores)`: the 0/1 tags of scores already computed, so that `predict(raw_problems)` is `predict_from_scores(scores(raw_problems))`, which `check_tagging_method` checks, and the command line scores each problem once; and `tag_thresholds()`: the per-tag thresholds that `predict_from_scores` applies, floats indexed by `tags` (`inf` for a tag it never predicts), which `check_tagging_method` checks against `apply_thresholds`, so a score can be shown beside its threshold). A bag of fold models is a score method too: its scores are the fold models' mean probability, its dev rows their out-of-fold scores with thresholds cross-fitted across the dev folds, and its thresholds those chosen on every out-of-fold score (ADR 0005). A fitted 0/1 method gets its dev predictions from `cross_predict`; a composite method, which fits on other methods' outputs, declares `depends_on` and passes `features=` to it (a calibrated Jev twin reads its base's committed files instead and sends no request: The calibrated Jev twins below). A rule-based or other method is kind `other`. An API method (one that sends paid requests) is a prompted method of kind `zero_shot` or `fitted`, served by the LLM toolkit below, unless its API answers a probability per tag (TypeSafe's Jev): that is a score method with commands of its own, under [ADR 0007](docs/adr/0007-api-score-methods-share-the-llm-toolkit.md) (TypeSafe methods below). Any method, whatever its kind, whose rules or settings were chosen while reading dev data records `method_entries["dev_in_sample"] = true` ([ADR 0004](docs/adr/0004-tagging-method-framework.md)). A method whose idea, rule or settings came from reading a test score also records `method_entries["test_informed"]` ([ADR 0011](docs/adr/0011-platt-lipton-threshold-rule.md)): it is never eligible for the command line either.
3. **Save only data.** JSON, CSV, `.npz`, skops (with the exact trusted types pinned by a test), safetensors, ONNX (`skl2onnx`, run with `onnxruntime`). Never `pickle`, `joblib`, `torch.save` or `torch.load` (ruff's `TID251` fails CI on them). Never dataset text: a method that keeps problems (e.g. few-shot examples) stores their `sample_id`s and the sha256 of their fields, and its `load` reads the texts from the dataset and checks the hashes. Pretrained weights are never in the folder either: it holds `pretrained.json` and only what was trained (e.g. the LoRA adapter, the head, the thresholds), written with `safetensors.torch.save_file` and JSON (both rules: ADR 0004). Trained weights over the folder's caps stay in the trained cache, which `trained.json` pins by hash ([ADR 0006](docs/adr/0006-trained-weight-cache.md)). Training never writes Trainer checkpoints, `save_model` or `save_state` output into the folder (any checkpoints go under `experiments/`) and sets `report_to="none"`; the method's training test asserts that no file under its output directory starts with pickle header bytes (`starts_like_pickle`). Cache arrays with `cache.ArrayCache`, never `Pipeline(memory=...)` (joblib pickles); the cache is a fit-time option only: `load` returns the method with no cache.
4. **Register.** Add one line to `METHODS` (`module`, `kind`, `requirements`, `groups`, and, when they apply, `calls_api` for every method that sends paid requests, `score_atol`, `depends_on`, `input_columns`), sorted by name. Put heavy dependencies in a new `pyproject.toml` dependency group, not in `default-groups`, and follow the CI recipe below for the method's tests, lint and CI job.
5. **Test.** Call `check_tagging_method(...)` in the method's tests.
6. **Freeze.** `uv run python -m codeforces_tags.methods.<package> freeze`: `check_dataset()`, refuse a dirty tree unless `--allow-dirty`, write `predictions.csv` (dev rows out of fold, test once), `scores.csv` (score methods) and `run_record.json` with `freeze_predictions`, save the method folder to `model_dir(name)` with `save_method`, and call `log_method`. Both `make_run_record` (`split_path=`) and `log_method` (`split=`) get the split that `--split` named, so the record and the logged datasets pin the split the predictions came from. The method's own `settings.py` values go in `method_entries["settings"]` and in its `recipe_sha256`; `RunRecord.settings` holds only the project-wide `settings_snapshot()`. A method that is not bit-reproducible records device, dtype and batch size in `method_entries`. `freeze` sets `method_entries["supersedes"]` itself (ADR 0004). A second run only checks and mirrors to MLflow: it re-derives the predictions only when `score_atol == 0`; otherwise it checks the frozen files (`check_frozen_method`) and the stored `recipe_sha256`.
7. **Verify**, at two levels (`uv run python -m codeforces_tags.methods.<package> verify`; a prompted method's is `python -m codeforces_tags.llm verify`, LLM toolkit below, and a TypeSafe method's is its package's own, TypeSafe methods below):
   - (a) for every local method, offline and without training: recompute the dev 0/1 rows and thresholds exactly from `scores.csv` (`cross_fitted_thresholds`, `apply_thresholds`; `load_scores` reads it exactly), recompute every metric from `predictions.csv`, and re-predict the test rows with `load_method(model_dir(name))`, comparing its `ScoreMethod.scores` with `scores.csv`. Scores are compared at `atol = max(score_atol, config.TUNING_EXPORT_TOLERANCE)` (rtol 0; 1e-9 absorbs another machine's BLAS); test 0/1 rows are exact when `score_atol == 0`, and otherwise a flip is allowed only where the frozen score lies within `score_atol` of `thresholds_`, and flips are counted and reported (a 0/1 method without scores re-predicts its test rows exactly);
   - (b) the full re-derivation: run by `verify` by default when `score_atol == 0` (e.g. `label_prior`), and only under `verify --retrain` otherwise, in which case the method's PR description quotes one `--retrain` run. It compares the re-derived scores with `scores.csv` at the tolerance of (a), and allows a 0/1 flip only where the frozen score lies within `score_atol` of the frozen threshold of its fold (dev) or of `thresholds_` (test). A method trained on a GPU, which no tolerance per score can hold, passes instead on bounds its settings declare before any retraining (ADR 0005).
8. **MLflow and latency.** Run `uv run python -m codeforces_tags.tracking datasets` (once per store), then `tracking latency --method <name>` (with `--max-cost-usd X` for an API method, which it times on live requests) and `tracking evaluate --method <name> --part dev` (then `--part test`, once, after the dev run of every method of the store); commit the frozen files. Without `--method`, `tracking evaluate` evaluates every frozen registered method, and refuses before the first run when one of them has no logged model in the store. An evaluation run that stopped or that `check_traces` refused is discarded with `tracking discard --run <run id>`, which deletes its traces too: deleting it in the MLflow UI keeps them, linked to the method's logged model. The zero-shot LLM methods need no key for this: `tracking evaluate` scores their frozen predictions and reads their `per_problem.csv`, so a store gets their evaluation runs with no paid call (`notebooks/README.md`, Figures). Evaluate every method on dev before the store's first test run: the screenshots of notebook 05 show the time window of the dev runs, and refuse a store where a test run falls in it. A method that joins a store which already holds test runs needs a new store, rebuilt in that order: move `experiments/mlflow.db*` and `experiments/mlartifacts/` aside, then follow `notebooks/README.md`, Figures; a dev run added to the old store makes the screenshots impossible to retake.
9. **Notebook.** Add `notebooks/NN_<name>.ipynb`, which reads frozen files only and compares with `label_prior` and `tfidf` through `analysis/comparison.method_scores`. Notebook 05 is the zero-shot LLM methods' (`05_zero_shot_llm.ipynb`); parallel sessions take the next free number at merge time.

### Tests and CI for a method's dependency group

Every test runs offline on synthetic fixtures: the default CI job has no dataset, no `openai`, no `playwright`, no deep-learning library and no API key, and a method's own job installs only its group, offline. A method whose tests need its group's libraries (e.g. `torch`) keeps them in `tests/methods/<package>/`, and its pull request adds:

1. in `pyproject.toml`: `--ignore=tests/methods/<package>` in pytest `addopts`; `src/codeforces_tags/methods/<package>/*` and `tests/methods/<package>/*` in `[tool.coverage.run] omit`; the group's import names (e.g. `torch`, `transformers`, `peft`, `safetensors`) in `[tool.pylint.typecheck] ignored-modules`, so the default pylint job still lints the package (without it, pylint reports `E0401` on `import torch`);
2. a `ci.yml` job for the group, which sets `HF_HUB_OFFLINE=1` and runs `uv sync --locked --group <group>`, then `uv run pytest tests/methods/test_registry.py tests/methods/<package> --cov-config=tests/methods/<package>/coverage.toml` (a `coverage.toml` of its own, with `source_dirs` set to the two folders and no `omit`; an `addopts` `--ignore` does not block a path passed explicitly), then `coverage report --include="src/codeforces_tags/methods/<package>/*" --fail-under=95` and `coverage report --include="tests/methods/<package>/*" --fail-under=100`;
3. tests that build tiny random models from a config, never downloading weights; a test that loads a method folder saves the tiny model's safetensors into `tmp_path`, writes a `pretrained.json` with their hashes, and sets `$CODEFORCES_PRETRAINED_DIR` (`monkeypatch.setenv`), which the isolation subprocess of `check_tagging_method` inherits;
4. a check that its `__main__.py`, imported in a fresh interpreter, in a coding agent's shell, lets MLflow start neither its telemetry nor its hint: `tests/tracking/test_environment.py` checks only the commands the default job can import (`COMMANDS` leaves out a registered method's package whose group `installed_methods()` lacks). A test of the package does it (`tests/methods/modernbert/test_main.py`), or the group's job also runs `"tests/tracking/test_environment.py::test_no_command_lets_mlflow_start_telemetry_or_hint"`, as the `f2llm` job does.

The default job's 95% package floor and 100% test-line rule are thus unaffected, and the method's job holds its own code to the same floors. A method that calls an LLM through a provider's SDK (dependency group `llm`, or `llm-<provider>`) imports it lazily and fakes it in its tests, so its tests stay in the default job and need no recipe. The `finetuning` group (the ModernBERT methods) and the `f2llm` group follow the recipe; `tests/methods/f2llm/test_packaging.py` pins the `f2llm` group's requirements, lock entry, `--ignore`, coverage `omit`, pylint `ignored-modules` and CI job. A command module also sets an environment variable under a str literal key (`os.environ["CODEFORCES_DEVICE"]`, not a constant's name): `test_only_mlflow_env_sets_mlflow_environment` counts any other key as a possible MLflow variable.

### LLM toolkit

A prompted method asks an LLM for each problem's tags through a fixed prompt ([ADR 0003](docs/adr/0003-api-methods-are-fixed-reference-models.md)). It is a `PromptedLlm` (`llm/prompted.py`) of kind `zero_shot`, or, for a method that learns from dev labels (e.g. few-shot), a subclass of kind `fitted` with `fit(raw_problems, labels)` and `request_context(raw_problems)` (each problem's own template variables, e.g. its examples), whose folder stores its examples' `sample_id`s and the hashes of their fields (`llm.prompts.field_sha256s`), never their text: its `load` reads the texts with `read_samples()` and checks the hashes, as the fake `tests/llm/fakes/prompted_fakes/few_shot.py` does. Its registry line has `calls_api=True` and the provider's dependency group (`llm` for OpenAI). Its package, the module that `MethodSpec.module` names (it may register several methods, e.g. one per output format), gives:

- `load(folder)`: for a zero-shot method, `codeforces_tags.llm.prompted.load_prompted`;
- `llm_spec(name) -> LlmMethodSpec`: the prompt name; the template path and, for `json`, the schema path (POSIX paths relative to the package: one versioned prompt file, `templates/<prompt>.v<version>.yaml`, for both, or a `.j2` template and a `.json` schema; the frozen zero-shot method folders keep the `.j2` and `.json` paths they were frozen with) and schema name (`None` for `text`); the problem fields and the constants the template renders; the `LlmSettings` (provider, model, reasoning effort, temperature, top_p, maximum output tokens, output format); the tags the model chooses from; and, in `extra`, a fitted method's own settings (e.g. its number of examples);
- `prompt_family(prompt_name) -> tuple[LlmMethodSpec, ...]`: the methods of one prompt, in the order their versions are registered (`text`, then `json`), never the order of `METHODS`;
- for a fitted method, `make_method(name)`: a fresh, unfitted method;
- optionally, `verify_extra(raw_problems)`: the package's own checks, which `llm verify` runs on every dev and test problem.

The method's settings live in its package's `settings.py`, and its templates (Jinja2, rendered by `templating.py`, with no `{% include %}`) and schema in the package, in versioned prompt files (`prompt_files.py`, read by `prompt_snapshot`, which checks each file's name and output format against the spec; [ADR 0009](docs/adr/0009-versioned-prompt-files.md)); the toolkit's transport settings (`LLM_*`), model prices (`LLM_PRICES`) and parser version (`TEXT_PARSER_VERSION`) live in `config.py`. A new provider adds one module, `llm/providers/<provider>.py` (`SDK_MODULE`, `request_body(request)` and `ask(settings)`, its SDK imported inside `ask`), one line in `PROVIDERS`, a price line per model and a dependency group `llm-<provider>`; usage and prices count input, cached input, output and reasoning tokens (`client.USAGE_KEYS`, `answers.cost_usd`), so a provider that bills another kind of token (e.g. cache writes) extends both. The package needs no `__main__.py`: the toolkit's commands serve it (`uv run --group llm python -m codeforces_tags.llm ...`; they read the dataset of `$CODEFORCES_DATA_DIR`, as a fitted method's `load` does, and the frozen split `assets/split/split.csv`, and take no `--data` or `--split`, so no gate can be pointed at another file), in this order:

1. `render --method M --part P --limit N --out DIR`: writes the exact prompt and request body of the first N problems of a part, for review; it sends nothing.
2. `run --method M --part dev [--max-cost-usd X]`, then commit `assets/methods/<name>/answers_dev.jsonl`; then `run --method M --part test`, and commit `answers_test.jsonl`. `run` sends the requests that have no answer yet and appends each answer as it arrives, once the dataset, the clean tree (`--allow-dirty`), the committed split and self-identifying slice and both answers files pass their checks and the prompts are registered; an answers file is only appended to (each holds every line of its committed versions, failed answers included), the test part waits until the dev answers file is committed, unchanged and complete, and the dev part sends nothing once the test part has answers. It needs the provider's API key only when requests are left, and exits with 1 while some are left (at the cost cap, after a transient error): run it again to send them.
3. `score --method M`: once the split and both answers files are committed and unchanged, and the answers files are complete and only appended to, it freezes `predictions.csv`, `per_problem.csv`, `run_record.json` and the method folder, with the prompt version pinned, and logs the method with `log_method`; a second run only checks the files and mirrors them.
4. `verify --method M`: offline, it renders every request again against its answer's hash, parses every answer again, checks the answers files' hashes in the run record and that each was only appended to, re-derives the frozen files, checks that the method folder builds the answered requests, then runs `verify_extra`.
5. `uv run --group llm python -m codeforces_tags.tracking latency --method M --max-cost-usd X`: times 50 live requests, one problem each, outside the answers files; the bulk time comes from the answers files.

The method never changes after its first dev request (ADR 0003): its prompt, schema, fields, constants and answer-shaping settings are in every request's hash, and `run` refuses answers files whose lines are under other hashes, so starting over is a new method with a new prompt name. A free-text answer is read by the fixed parser `parse_text_tags`, and a failed answer (a status other than `completed`, or unreadable JSON) scores as the empty tag set and is counted. Tests send no request and read no API key: they inject a fake `Ask`, monkeypatch `codeforces_tags.llm.client.ask_for` (which a loaded `PromptedLlm` calls, so `check_tagging_method`'s round trip predicts offline) or put a fake SDK module in `sys.modules`, as `tests/llm/test_main.py` does with the fake packages of `tests/llm/fakes/prompted_fakes/`.

### TypeSafe methods

The two TypeSafe methods, `jev-statement` and `jev-statement-code`, ask TypeSafe's Jev model one Noul question per focus tag (would Codeforces put the tag on this problem, given the tag's definition) and read the probabilities it answers ([ADR 0007](docs/adr/0007-api-score-methods-share-the-llm-toolkit.md)). Each is registered as a score method that calls an API (`calls_api=True`, dependency group `llm-typesafe`), served by `src/codeforces_tags/methods/typesafe_jev/` and not by the LLM toolkit's commands, which read a tag set from text. Its answers are `LlmAnswer` lines in the toolkit's append-only answers files, under the rules of [ADR 0003](docs/adr/0003-api-methods-are-fixed-reference-models.md). `jev-statement` sends the statement and `jev-statement-code` the statement and the solution, with identical questions, so whether the solution helps is concluded on dev. The package has `settings.py` (the pinned model `jev-1.13.0`, never the alias `jev-latest`; the convention, the question (a Jinja2 template) and each focus tag's tag definition, read from the versioned prompt file `templates/jev-tags.v1.yaml` (`read_prompt_file`, [ADR 0009](docs/adr/0009-versioned-prompt-files.md)), frozen since the first dev request and in every request's hash and in each method's recipe; the transport settings, which are in neither), `questions.py` (the questions, each problem's state and `JevRequest`, hashed as the exact bytes the SDK sends), `client.py` (`jev_session()`, the only place that imports `typesafe_sdk`), `answers.py` (the probabilities, the summary and the served-model check of the answers), `runner.py` (`send()`: concurrent requests under a cost cap), `method.py` (`JevTagger`, whose `scores_from_answers()` scores the answers it already holds, so that the command line's prediction is one request, and `load(folder)`), `tracking.py` (the prompt `jev-tags` in the prompt registry, one version per prompt file, each tagged with its file's sha256 and `sha256_json(SETTINGS)`: `register_jev_prompt()` and `link_jev_prompt()`) and `__main__.py`. A failed answer (a refused request, or a body that is not eight probabilities from 0 to 1) is a final line that scores 0.0 on every tag and is counted; a timeout or a rate limit writes no line, and the next `run` sends that request again.

The commands run as `python -m codeforces_tags.methods.typesafe_jev <command> --method M`, with M one of the two methods, the searched Jev method (next subsection) or, for `export`, `freeze` and `verify`, a calibrated twin (The calibrated Jev twins, below). Like the toolkit's, they read the dataset of `$CODEFORCES_DATA_DIR` and the frozen split `assets/split/split.csv`, and take no `--data` or `--split`. `TYPESAFE_API_KEY` is read only when requests are left to send, from the gitignored `.env` of the main checkout. A worktree has no `.env` of its own, so the commands that send requests run as `uv run --env-file "$(git rev-parse --path-format=absolute --git-common-dir)/../.env" --group llm-typesafe python -m codeforces_tags.methods.typesafe_jev <command> --method M`. In this order:

1. `render --part P --limit N --out DIR`: writes the request body of the first N problems of a part, for review; it sends nothing. It is the last moment to change a word of a definition without a new method.
2. `run --part dev [--max-cost-usd X]` (2 USD by default) for both methods, then commit each `answers_dev.jsonl`; then `run --part test` for both, and commit each `answers_test.jsonl`. `run` checks the dataset, the clean tree (`--allow-dirty`), the committed split and self-identifying slice, that each answers file was only appended to and every line is under its problem's current request hash, and that no completed answer came from another model than `jev-1.13.0`, then, for the two frozen methods, registers the prompt `jev-tags` in the store's prompt registry before it sends a request (`--tracking-uri`, `--artifact-dir`); the test part waits until the dev answers of every method of its study (`settings.STUDIES`: the two methods here) are committed, unchanged and complete, and the dev part sends nothing once its test part has answers. It stops sending after 20 failed answers in a row (`MAX_FAILED_IN_A_ROW`: a refused request costs nothing, so the cap never stops a run of them). It exits with 1 while requests are left (the cost cap, a run of failures, a transient error): run it again, once any failed lines are understood.
3. `freeze`: once both answers files are committed, unchanged and complete, it freezes `predictions.csv` (dev out of fold, test once), `scores.csv` (the probabilities), `per_problem.csv`, `run_record.json` and the method folder (`jev.json`, with the thresholds), and logs the method with `log_method`; a second run only checks the files and mirrors them. A run record made now pins `prompts:/jev-tags/1`, registered first; a frozen record is never rewritten, and the two frozen ones pin no prompt. Every run then links the prompt to the method's logged model and run. The searched method's words are not a version of `jev-tags` (next subsection): its record pins no prompt, and none is linked to it. It needs the `llm-typesafe` group installed, since the run record and the logged model pin `typesafe-sdk`, and no key.
4. `verify`: offline, with no key and no SDK, it rebuilds every request against its answer's hash, checks the served model, that each answers file was only appended to, the run record (with the commit that last changed each answers file, a check that needs the original development history, which the public snapshot of one squashed commit does not hold; the sha256 checks still hold) and the method folder's thresholds, and re-derives every frozen file from the answers files.
5. `tracking latency --method M --max-cost-usd 0.05` (with the `--env-file` and the group: it times 50 live requests, outside the answers files), `tracking datasets` (once per store), then `tracking evaluate --method M --part dev` for both methods, and only then `--part test` for each (neither the group nor the key is needed: it scores the frozen predictions and never pins the requirements). Every method of a store is evaluated on dev before the store's first test run, and a store that already holds test runs is rebuilt first (step 8 of Adding a tagging method).

Push only after `freeze`: `tests/test_conformance.py` checks every folder of `assets/methods/` against the split, so a folder that holds answers files only fails CI, and the answers commits stay local until the frozen files are committed with them. ### The searched Jev method

`jev-statement-code-gepa` is Jev with words that a search chose ([ADR 0010](docs/adr/0010-searched-jev-words.md)). GEPA 0.1.4 (`gepa`, in the `modeling` group; `gepa.optimize`, called directly with the adapter of `tuning.py`) rewrites the nine pieces of `jev-statement-code`'s words, the convention and the eight tag definitions (`words.PIECES`), with `gpt-6-luna` at high reasoning effort as the reflection model, asked through the LLM toolkit's OpenAI adapter (`REFLECTION_SETTINGS`); the question stays `settings.QUESTION`. The protocol is fixed before the search, in `settings.py` (`SEARCH_*`): each iteration draws 40 problems of the learning folds 1-3, with 2 positives of each focus tag (`StratifiedSampler`), and the reflection model rewrites one piece from their worst errors; every accepted candidate words are scored on the whole selection fold 4; the held-out fold 0 is never read, and the adapter refuses its sample ids. GEPA maximises one minus each problem's balanced Brier term (`objective.problem_scores`), and the chosen candidate words are those with the best mean score on the selection fold among the candidates that pass the dataset-text check (no 8-word sequence shared with a problem's statement, notes or solution, outside the seed words), the lowest index on a tie. The search stops at 200 iterations or once $15 is spent on Jev and the reflection model together.

Its requests are the search's records, not the method's answers: they stay in `experiments/jev-statement-code-gepa/search/` (gitignored; GEPA's `run_dir`, whose state file is a pickle, is never set), so `tune` run again replays the search from them at no cost, then goes on. Only the record is committed: `export` writes `assets/methods/jev-statement-code-gepa/tuning/` once (`tuning/params.json`, with the chosen words, `candidates.csv`, `candidates/<index>.json` and `history.csv`), after checking that the search stopped at a cap, that the seed's mean score on the selection fold equals the one recomputed from `jev-statement-code`'s frozen `scores.csv` (within `TUNING_EXPORT_TOLERANCE`), and the dataset-text check; a second `export` only checks. The method then answers every dev and test problem afresh with the chosen words, in its own answers files, and is frozen like the other Jev methods. Its words are data: `words_of()` reads them from `tuning/params.json`, its method folder holds them in `model/words.json`, its recipe hashes them, and `load` refuses words whose hash differs from `jev.json`'s. They are a search's frozen result, not a hand-written prompt version: no versioned prompt file holds them ([ADR 0009](docs/adr/0009-versioned-prompt-files.md) covers the prompt files, the frozen methods' `jev-tags.v1.yaml` among them), so its `run` registers no prompt and its run record pins none. It is `dev_in_sample` (its run record's `method_entries` also hold `search`: the folds, the chosen candidate, the sha256 of `params.json`, the search's cost, and the held-out fold's macro F1 and per-tag F1), so it is a reference, never eligible for the command line, and its honest comparison with `jev-statement-code` is on the held-out fold. The dev-before-test gate is per study (`settings.STUDIES`): the two frozen methods form one study and the searched method its own, so its `run --part test` waits for its own dev answers only; its `run` also refuses until `tuning/params.json` is committed and unchanged.

The search is logged to MLflow in its own experiment, `jev-gepa`, never in `tag-methods`: a parent run `search-jev-statement-code-gepa` with one step per iteration, one nested run `candidate-<index>` per candidate scored on the selection fold, and one prompt per piece, `jev-gepa-<piece>` (`search_tracking.prompt_name()`), with one version per change, made with `create_prompt_version`. `tune` logs it live, and `log-search` replays `tuning/` into an empty store, adding nothing the store already holds, with no key.

The commands run as `python -m codeforces_tags.methods.typesafe_jev <command> --method jev-statement-code-gepa`, in this order (Commands, The GEPA search over Jev's words):

1. `tune [--max-cost-usd X]` (15 USD by default), with `--group llm --group llm-typesafe` and the main checkout's `--env-file`: it checks the dataset, the clean tree (`--allow-dirty`), the committed split, the self-identifying slice and the seed's frozen files, runs or replays the search, logs it live and prints one line per iteration. It reads `OPENAI_API_KEY` and `TYPESAFE_API_KEY` only when uncached requests are left, and refuses once the search is exported (`tuning/params.json` exists: its words are final). It exits with 1 when the search is interrupted inside an iteration: after a transient error of Jev or the reflection model, or a run of Jev's failed answers, run it again; after its cost cap was spent inside a call, run it again with a higher `--max-cost-usd` (the same cap stops it at the same point).
2. `export`, then commit `tuning/`.
3. `log-search`: replays the record into the store.
4. `run --part dev`, `run --part test`, `freeze`, `verify`, `tracking latency --max-cost-usd 0.05` and `tracking evaluate`, as steps 2 to 5 of TypeSafe methods. The answers commits stay local until `freeze` has written the other frozen files (Push only after `freeze`, above).

Tests send no request and read no key: the fake `typesafe_sdk` of `tests/methods/typesafe_jev/conftest.py`, a fake reflection `Ask` (`codeforces_tags.llm.client.ask_for` monkeypatched, or `ask=` passed) and GEPA's real engine on synthetic problems; one of them replays a finished search and asserts that it sends nothing and gives the same candidates. `notebooks/10_jev_gepa.ipynb` reads the frozen files: what the search changed, how it went and what it cost, the held-out fold against `jev-statement-code`, all of dev labelled in sample, and the test set, reported once.

### The calibrated Jev twins

`jev-statement-code-platt` and `jev-statement-code-gepa-platt` are the calibrated twins of `jev-statement-code` and `jev-statement-code-gepa`: the same Jev probabilities under another threshold rule, Platt then Lipton ([ADR 0011](docs/adr/0011-platt-lipton-threshold-rule.md)). The F1 argmax can jump between almost equal peaks of a tag's F1 curve (four runs within 0.01 of its maximum for the `probabilities` of `jev-statement-code-gepa`), depending on which four folds choose it; the new rule reads the curve's height, which is stable. It is fixed in ADR 0011 before any new number: it was proposed after the dev F1 curves and a test score were read, and declared with R0 and R1 before `export` computed the twins' records, so their nested choice measures only the choice among these three rules. For one tag, `lipton_threshold()` fits a Platt map on logit(p) (`platt_fit()`, which refuses a slope at or below 0), takes F1\* from `best_f1()` (the F1 at `best_threshold`'s cut), cuts the calibrated probability at F1\*/2, maps the cut back to a raw threshold and snaps it to Jev's 0.01 grid (`snap_to_grid()`: the midpoint below a grid value, so that a failed answer's 0.0 is never predicted); `RULE_SETTINGS` holds its constants, built from `config.PLATT_CLIP`, `config.SCORE_GRID`, `config.PLATT_SOLVER` and `config.PLATT_TOL` (the Platt map is fitted to convergence, `rule_calibrator()`). `PlattLiptonThresholds` (`model/platt_lipton.py`) subclasses `CrossFittedTagThresholds` and overrides only the choice of thresholds: fold k's come from the other four folds' out-of-fold scores, the final ones from all of them.

A twin is a composite over its base (`MethodSpec.depends_on`, `settings.PLATT_BASES`): a score method with `calls_api=True`, no answers files of its own, no request and $0. It reads its base's committed answers files, `scores.csv` (its own `scores.csv` holds the same probabilities), `run_record.json`, `latency.csv` and `per_problem.csv` (both copied byte for byte, since a prediction is the same request and each problem's recorded call is the base's). Its words are its base's (`words.base_of()`, `words_of()`), and its recipe holds the base's settings hash and `RULE_SETTINGS`. `run` and `render` refuse it. Its `jev.json` holds its own name and thresholds, so a loaded twin asks Jev its base's requests and applies its own thresholds. It is `test_informed` (`settings.TEST_INFORMED`: the rule was proposed after the test score of `jev-statement-code-gepa` was read), so it is never eligible for the command line, and its test score, scored once, is a reference. It is `dev_in_sample` as its base is: false for `jev-statement-code-platt`, true for `jev-statement-code-gepa-platt`.

The commands run as `python -m codeforces_tags.methods.typesafe_jev <command> --method <twin>`. Like the other Jev commands they read the dataset of `$CODEFORCES_DATA_DIR` and the frozen split, and none reads a key. In this order (Commands, Freezing the calibrated Jev twins):

1. `export` writes `assets/methods/<twin>/tuning/` once, from the dev rows of the base's `scores.csv` only (it never reads a test row), after checking the dataset, the clean tree (`--allow-dirty`), the committed split and that the base's `scores.csv`, `run_record.json` and answers files are committed and unchanged: `params.json` (the rule and `RULE_SETTINGS`, the base and the sha256 and commit of each base file, R2's final thresholds and the nested choice), `rules.csv` (the out-of-fold macro F1 and per-tag F1 of R0, the current F1 argmax, R1, Platt then 0.5, and R2, with each one's paired difference from R0 and group-bootstrap intervals), `nested.csv` (for each outer fold, the rule that wins inside the four other folds) and `stability.csv` (each tag's five fold thresholds under R0 and R2, and the dev problems whose 0/1 depends on which four folds chose). The twin's rule is R2 whatever these show. A second `export` checks the base's files against `params.json`, as `freeze` does (step 2), then compares byte for byte. Commit `tuning/` before freezing.
2. `freeze` refuses until the four files of the twin's `tuning/` (`settings.PLATT_FILES`) are committed and unchanged, every base file that `tuning/params.json` names is committed, unchanged, and has the sha256 and, as its last commit, the commit that it records (a change and its revert give back the bytes but not that commit, so a base file changed after the twin's export means a new twin; and a squash, a rebase or a shallow clone drops the commit from HEAD's history: merge the pull request that holds the base's files with a merge commit, and work in a full clone; these commit checks need the original development history, which the public snapshot of one squashed commit does not hold, while its sha256 checks still hold), and the base's `latency.csv` and `per_problem.csv` are committed and unchanged. It freezes `predictions.csv` (dev out of fold under R2, test once with R2's final thresholds), `scores.csv`, `run_record.json` (`method_entries`: `settings`, `base`, `served_models`, `threshold_rule`, `dev_in_sample`, `test_informed` and `latency_from`), the method folder, and `latency.csv` and `per_problem.csv` (the base's, byte for byte); it writes nothing in the base's folder and logs the method with `log_method`, which tags its run `test_informed=true`; its record pins no prompt and it links none, since it sends no request of its own (only the two frozen methods' freeze links `jev-tags`); a second run only checks and mirrors. It needs the `llm-typesafe` group, since the run record pins `typesafe-sdk`, and no key.
3. `verify`: offline, it re-derives `predictions.csv`, `scores.csv`, the thresholds and `tuning/` from the base's committed files, and checks that the base's files have the recorded sha256 and last commits (the commits, as in step 2, only in the original development history), that the run record holds every entry that a freeze writes now (its `settings` included), and that `latency.csv` and `per_problem.csv` equal the base's.
4. `tracking latency --method <twin>` logs the committed `latency.csv` without timing anything and sends no request; then `tracking datasets` (once per store) and `tracking evaluate --method <twin> --part dev`, and only then `--part test` (step 8 of Adding a tagging method: every method of the store is evaluated on dev before the store's first test run, so a store that already holds test runs is rebuilt first, `notebooks/README.md`, Figures).

Tests send no request and read no key: they build a twin's base from the fake `typesafe_sdk` fixtures of `tests/methods/typesafe_jev/conftest.py`, and give `export` a scores frame whose test rows are NaN. `notebooks/11_jev_platt.ipynb` reads the frozen files: Jev's reliability before and after the Platt map, the stability of the thresholds, the declared comparison and the nested choice, each twin against its base, and the test set, reported once.

### F2LLM embedding methods

The four methods of `methods/f2llm/` need the `f2llm` dependency group (about 3 GB of torch and CUDA wheels) and the pinned F2LLM-0.6B weights (1.19 GB, downloaded once per machine): both downloads wait for the user's yes. The cache, the tuning journals and SetFit's adapters live under `experiments/`, so an interrupted run resumes. ```bash

```bash
export HF_HUB_OFFLINE=1            # from here on, nothing downloads

$M reference                       # assets/f2llm/tfidf_reference.csv; refused unless it reproduces TF-IDF's frozen scores
$M tune --method f2llm_probe && $M export --method f2llm_probe    # then f2llm_late_fusion and f2llm_early_fusion; ~3.5 h on the CPU
$M atol --device cuda              # measures score_atol: write it into _F2LLM_SCORE_ATOL in methods/__init__.py and commit it before any freeze
$M freeze --method f2llm_probe     # then f2llm_late_fusion and f2llm_early_fusion (f2llm_setfit, not frozen, would take ~5-7 h)
$M verify --method f2llm_probe f2llm_late_fusion f2llm_early_fusion    # the frozen ones, on the CPU; and with --retrain --device cuda
```

`verify` re-predicts the test rows on the CPU by default; `--device auto` takes the device a loaded method takes (the GPU when torch sees one), and `--device cuda` the GPU. `--single` scores each test problem in its own call, as the command line predicts one exercise, and on the GPU its live re-prediction always does, with or without it: one batch of every test problem at sustained full power rebooted this machine once. `embed`, `atol` and `freeze` (`--device cuda` by default) and `verify --retrain --device cuda` are batched GPU work, the same kind of load (`f2llm_setfit`'s `freeze` and `--retrain` also encode every test statement in batches): run them only when that work is meant, one at a time, with `nvidia-smi` watched. `freeze` saves and checks its method folder on the CPU, where `score_atol` was measured.

Then `tracking datasets`, `tracking latency --method NAME` (with `uv run --group f2llm`, on an idle machine; it times the device a loaded method takes, so the committed `latency.csv` holds the GPU timings, one problem per call; the first timings, taken on the CPU under load, by choice, as their commit message in the original development history records, were moved to `analysis/cpu/latency.csv`) and `tracking evaluate`, as step 8 of the checklist says. The tests of the group run as the `f2llm` job runs them (Commands, above).

### Serving

Any frozen tagging method runs as a model server: MLflow's scoring server, in one Docker image per method, on local Docker, Kubernetes or SageMaker, on the CPU or the GPU as `CODEFORCES_DEVICE` says ([ADR 0012](docs/adr/0012-serving-tagging-methods.md); `serving/`, `deploy/` and `apps/` under Layout). `package` writes the method's MLflow model and its Docker build context in `build/serving/<method>/` (which may be a symlink to another disk: the folders it writes are compared by their resolved paths), from the committed method folder: it needs the method's dependency groups (`--group f2llm` for an F2LLM method, none for `tfidf`) and its weights in their caches, and refuses uncommitted code, `deploy/Dockerfile` or method folder unless `--allow-dirty`. `build` packages, then builds `codeforces-tags/<method>:<git short sha>` and `:latest`; once the build has succeeded, it removes the method's older images, BuildKit's cached build contexts (`docker builder prune --filter type=source.local`: every one on the host, not only this method's; they are caches, and a build sends its context again) and the staged weights (`--keep-previous` keeps them), and `clean-images` removes older images by itself. A first build downloads the base image and about 3.2 GB of wheels, so it waits for the user's yes, as every download does. `smoke` asks a running model server for the first 20 test-set problems, one request at a time, and compares them with the frozen test rows by the rule of `verify`'s level (a); it needs the dataset, and refuses a method that calls an API. Local Docker, for `f2llm_late_fusion`:

```bash
uv run --group f2llm python -m codeforces_tags.serving package --method f2llm_late_fusion   # the build context alone
uv run --group f2llm python -m codeforces_tags.serving build --method f2llm_late_fusion
METHOD=f2llm_late_fusion docker compose -f deploy/docker-compose.yml --profile cpu up --wait   # or --profile gpu
uv run python -m codeforces_tags.serving smoke --method f2llm_late_fusion
METHOD=f2llm_late_fusion docker compose -f deploy/docker-compose.yml --profile cpu down
uv run python -m codeforces_tags.serving clean-images --method f2llm_late_fusion   # or --keep IMAGE_ID, or --all
```

The `gpu` profile needs an NVIDIA driver of 580 or later and the NVIDIA Container Toolkit, and the two profiles share port 8080, so one runs at a time. On Kubernetes, the path checked here is kind, with the small `tfidf` image, which kind loads into its node; every kubectl call names the context, and the forward uses local port 18080, since compose holds 8080:

```bash
uv run python -m codeforces_tags.serving build --method tfidf
kind create cluster --name codeforces-tags --wait 120s
kind load docker-image codeforces-tags/tfidf:<git short sha> --name codeforces-tags
uv run python -m codeforces_tags.serving manifests --method tfidf --device cpu
kubectl --context kind-codeforces-tags apply -k build/k8s/tfidf-cpu
kubectl --context kind-codeforces-tags rollout status deployment/tfidf-model-server --timeout=300s
kubectl --context kind-codeforces-tags port-forward service/tfidf-model-server 18080:8080   # then, in another shell:
uv run python -m codeforces_tags.serving smoke --url http://127.0.0.1:18080 --method tfidf
uv run python -m codeforces_tags.serving manifests --method tfidf --device gpu
kubectl --context kind-codeforces-tags apply -k build/k8s/tfidf-gpu --dry-run=server
kind delete cluster --name codeforces-tags
```

`manifests` tags the image as `build` tagged it (the git short sha, with `-dirty` for uncommitted inputs), read from the packaged model and never `latest` (`--tag` names another), and `--registry R` names the registry another cluster pulls from, once `docker tag` and `docker push` have sent the image there (on the user's go). A method that needs an API key reads it from the Secret `codeforces-tags-env`, made before `apply -k`: `kubectl --context kind-codeforces-tags create secret generic codeforces-tags-env --from-env-file=deploy/.env.serving` on kind, with another cluster's context elsewhere. SageMaker runs only on the user's explicit go: the scripts push about 8 GB to ECR, the endpoint bills by the hour, and a method that calls an API is refused. `deploy.sh` also refuses a GPU endpoint (`DEVICE=gpu`) on an aws CLI that cannot set `InferenceAmiVersion`, such as this machine's 2.11.7, before anything reaches AWS, so the example is a CPU endpoint. `invoke.sh` sends `payload.json`, a request body of the model server (MLflow's `dataframe_split` of the raw input columns, as `serving.client.request_payload` writes it), and writes the endpoint's answer to `answer.json`:

```bash
export METHOD=f2llm_late_fusion DEVICE=cpu AWS_REGION=<region> ROLE_ARN=<execution role ARN>
deploy/sagemaker/deploy.sh
deploy/sagemaker/invoke.sh payload.json answer.json
deploy/sagemaker/delete.sh
```

The Streamlit app runs on the user's machine, against a model server of compose, `docker run`, `serving.local` or a cluster's forwarded port (a SageMaker endpoint takes only IAM-signed requests): `$CODEFORCES_SERVING_URL` (`http://127.0.0.1:8080` by default), with `$CODEFORCES_DATA_DIR` for the test-set problems. Its sidebar links the served method to the `tag-methods` experiment, its run and, for a prompted or Jev method, each prompt version its committed run record pins, then those linked to its run in the store (Jev's `jev-tags`), in the MLflow UI of `$CODEFORCES_MLFLOW_UI_URL` (`http://127.0.0.1:5000` by default). `mlflow-ui` serves the project's store there, on `127.0.0.1` and without the shell's API keys, tokens and proxies (`config.MLFLOW_SERVER_LEFT_OUT`), until Ctrl-C:

```bash
uv run python -m codeforces_tags.serving mlflow-ui   # then, in another shell:
uv run --group app streamlit run apps/streamlit_app.py
```

`up` runs all of it in one terminal: it checks everything before it starts anything (the method, the three ports, Streamlit, the store, then the image, or with `--local` the build context, which it packages when it has none), then starts the model server (compose, from the image `build` made, `--build` building it first and `--tag T` naming another tag than `latest`; or, with `--local`, `serving.local` on `build/serving/<method>/`, with the method's dependency groups), the MLflow UI (unless `--no-mlflow-ui`) and the app, which Streamlit opens in a browser (unless `--no-browser`), on ports 8080, 5000 and 8501 of `127.0.0.1` (`--port`, `--mlflow-port`, `--app-port`). `--allow-dirty` lets it package or build from uncommitted inputs, as `package` and `build` do. It prints where each part is, then stops all of them, the app first, on Ctrl-C, SIGTERM or SIGHUP (status 0; a second Ctrl-C does not interrupt the stop) or once one dies (status 1, after the end of its log); the logs of the UI and of the app are in `build/serving/<method>/up/`. `--device gpu` needs Docker's `nvidia` runtime (the NVIDIA Container Toolkit, driver 580 or later), which `up` checks first. A method that calls an API runs too, each prediction of the app a paid request, with its key read from `deploy/.env.serving` (Docker) or the shell (`--local`):

```bash
uv run --group app --group f2llm python -m codeforces_tags.serving up --method f2llm_late_fusion --local
```

`uv sync --group app` downloads streamlit, on the user's yes; a `--group app` command leaves it installed, which CI does not install: run `uv sync` before the CI commands above. Notebook 12 serves `f2llm_late_fusion` on the CPU with `serving.local`, and shows the recorded Docker, Kubernetes and SageMaker runs; it needs the dataset and the F2LLM weights:

## Data gotchas

Findings from `notebooks/01_dataset_overview.ipynb`:

- **Python 2 code**: 25% of `source_code` is Python 2. Read code with regexes or tokens; Python 3's `ast` fails on it.
- **Tagging methods take raw problems from `read_samples()` and preprocess inside their pipeline; analysis code uses `load_dataset()`.** Preprocessing drops repeated tags, turns the `-1` difficulty sentinel into NA, and fixes the scraping artefacts in the text. `preprocess()` works row by row, so prediction reuses it unchanged.
- **The 41 problems with no tags stay in the data**, as problems with an empty label set. A few look like tree, graph or game problems, so their labels may be incomplete.
- **Near-duplicates**: 82 pairs are the same problem, mostly easy/hard versions, and 69 of them share their focus tags. A pair split across train and test leaks data. Split by `near_duplicate_groups(df)`, never by row. It has two stages:
  - TF-IDF candidates at 0.4 on `prob_desc_description`;
  - the frozen verdicts of two LLM judges, in `assets/near_duplicates/judgments.csv`.

  Pass it the frame indexed by `sample_id`, as `load_dataset()` returns it; it raises on any other index, because the verdicts are keyed by sample id. Group the full dataset, never a subset: on a subset the TF-IDF is refit and can link unjudged pairs just under 0.4. Outside notebooks 01-03, which study the detector and build the split, nothing groups the dataset: everything downstream reads the frozen groups, `load_split()["group"]` or the `group` column that `select_part()` appends. A TF-IDF threshold alone fails: 0.8 misses 11 pairs, and 0.4 chains unrelated problems into groups of up to 11 (`notebooks/02_near_duplicates.ipynb`).
- **Split**: train and tune on `select_part(df, load_split(), "dev")` (its 5 folds for cross-validation), and score the test part once, at the end. Never re-split or tune on test. The split keeps near-duplicate groups whole, and balances the focus tags, their frequent pairs, the problems with no focus tag and the release year (`notebooks/03_train_test_split.ipynb`).
- **Model selection**: choose models on the cross-fitted out-of-fold macro F1 of the dev set, read errors on out-of-fold predictions, and freeze only the configuration chosen on dev ([ADR 0001](docs/adr/0001-model-selection-protocol.md)); every tagging method's `freeze` (or `llm score`) scores dev out of fold and test once; ADR 0004's rule names the eligible frozen method with the best dev out-of-fold focus macro F1 ([ADR 0004](docs/adr/0004-tagging-method-framework.md)), the CLI's default is the user's choice among the eligible methods, on dev and on a prediction's latency and cost, never on a test score ([ADR 0008](docs/adr/0008-cli-default-method.md): the rule names `descode2tag-json`, and the default is `jev-statement-code`, for its latency), and every other frozen method's test score is a reference, reported and never used to choose. `tuning freeze` scores the tuned model's test set once; notebook 04 reads it beside the logistic regression of its first section, its reference. The ModernBERT methods adapt ADR 0001 to fine-tuned transformers ([ADR 0005](docs/adr/0005-fine-tuned-model-protocol.md)): each tunes on one dev fold, since a trial takes 5 to 20 minutes, and is the bag of its five fold models, fixed before the test set is scored; its dev rows are the fold models' out-of-fold scores, on which the fine-tuned methods are compared. The searched Jev method `jev-statement-code-gepa` is `dev_in_sample` ([ADR 0010](docs/adr/0010-searched-jev-words.md)): its words were chosen on dev folds 1-4, so it is compared with `jev-statement-code` on the held-out fold 0, and its test score is a reference. The calibrated Jev twins are `test_informed` ([ADR 0011](docs/adr/0011-platt-lipton-threshold-rule.md)): their threshold rule was proposed after the test score of `jev-statement-code-gepa` was read, so they are never eligible and their test scores are references.
- **Time confound**: the share of `math` and the multi-test-case input format both rose after 2019. Statement words like "test cases" look like `math` signal only because of the release period.
- **Pretrained encoders may have seen the dataset**: F2LLM-v2's training data holds xCodeEval itself, so the F2LLM methods use v1, and Qwen3's undisclosed pretraining may still include Codeforces pages. An embedding method's gain over TF-IDF is an upper bound; notebooks report every score also without the self-identifying problems (`config.SELF_IDENTIFYING_FILE`).
